# 02. ФИЛОСОФИЯ SUPERAPP

SuperApp — интеллектуальная рабочая система риэлтора, которая помогает не упускать клиентов, находить подходящие объекты и доводить рабочие возможности до сделок.

Продукт создаётся для рынка недвижимости Узбекистана.

Долгосрочная концепция — **«смартфон для бизнеса»**: единая базовая платформа с независимыми подключаемыми модулями.

Основные направления:

- Lead Shield.
- Unified CRM Inbox.
- Client 360°.
- AI Client Rescue.
- Today / Next Best Action.
- Property Hub.
- Smart Match.
- Showing Manager.
- Deal Management.
- Commission Tracking.
- AI Copilot.
- Agency Management.
- Analytics.

Единый CRM Inbox — одно из центральных оснований всей платформы.

Он обеспечивает входящий поток информации для следующих процессов:

**Обращение → Контакт → Клиентский запрос → Следующее действие → Подбор объекта → Показ → Сделка.**

Но не каждое сообщение должно автоматически становиться клиентом или сделкой.

Например:
- Вопрос от нового покупателя может стать потенциальным лидом.
- Пропущенный рабочий звонок может потребовать обратного контакта.
- Сообщение существующего клиента пополняет историю.
- Сообщение от собственника может относиться к уже существующему объекту.
- Рекламное или нерелевантное сообщение может быть исключено из активной рабочей очереди после проверки.

Таким образом, Inbox не только собирает события, но и помогает превратить полезные обращения в управляемую работу.

# 03. ГЛАВНАЯ ЦЕЛЬ ЭКРАНА

После открытия Inbox риэлтор должен за 3–5 секунд понять:

1. Сколько рабочих обращений действительно требуют ответа.
2. Какие пропущенные звонки ещё не обработаны.
3. Какие новые сообщения поступили.
4. Какие обращения назначены лично ему.
5. Есть ли заявки без ответственного.
6. Какие источники подключены, а какие временно недоступны.
7. Как быстро открыть клиента или выполнить следующее действие.

Главная пользовательская мысль:

**«Все мои доступные рабочие обращения здесь. Я вижу, что ещё нужно обработать».**

Для руководителя агентства:

**«Я могу проверить, что ни одна доступная командная заявка не осталась без ответственного».**

Для сотрудника:

**«Я вижу свои обращения и могу быстро продолжить работу с каждым клиентом».**

# 04. ОСНОВНЫЕ UX-ПРИНЦИПЫ

## Принцип 1. One Inbox, Multiple Sources

Разные рабочие каналы отображаются в одном согласованном интерфейсе.

Но интерфейс не должен скрывать происхождение обращения.

Каждый элемент списка показывает источник.

## Принцип 2. Action-Oriented

У каждого обращения есть понятный статус и допустимое следующее действие.

Не превращай Inbox в бессмысленную историю сообщений.

## Принцип 3. No False Certainty

Система должна различать подтверждённые факты и отсутствие информации.

Не называй клиента потерянным без подтверждения.

Не считай исходящее намерение подтверждённым ответом.

## Принцип 4. Human in Control

AI может предлагать действия и черновики, но человек должен контролировать отправку сообщений, объединение контактов и существенные изменения клиентской базы.

## Принцип 5. Mobile First

Основные действия доступны одной рукой.

Риэлтор может использовать приложение между звонками, во время показа и в дороге.

## Принцип 6. Privacy by Design

Личные и корпоративные данные не смешиваются автоматически.

Пользователь видит только источники и обращения, доступные ему по правам.

## Принцип 7. Source-Aware

Для каждого канала учитываются реальные ограничения API и разрешений.

Нельзя считать все каналы функционально одинаковыми.

# 05. ВИЗУАЛЬНЫЙ СТИЛЬ

Используй утверждённую дизайн-систему SuperApp.

**Apple Minimalism / iOS 26-inspired.**

## Цвета

- Background: #FFFFFF.
- Primary Text: #000000.
- Secondary Text: #737373.
- Tertiary Text: #909090.
- Card Surface: #F7F7F7.
- Secondary Surface: #FAFAFA.
- Border: #E8E8E8.
- Primary CTA: #000000.
- CTA Text: #FFFFFF.
- Selected Filter: #000000.
- Selected Filter Text: #FFFFFF.
- Unselected Filter: #F5F5F5.
- Unselected Filter Text: #333333.

Используй сдержанные семантические цвета только для реальных статусов:

- Красный — подтверждённая ошибка либо существенная просрочка.
- Оранжевый — предупреждение или необходимость проверки.
- Зелёный — подтверждённое успешное действие или работающее подключение.

Не раскрашивай каждую карточку по источнику.

Логотипы Telegram, WhatsApp и Instagram могут сохранять официальные узнаваемые элементы в рамках их бренд-правил, но общий дизайн остаётся преимущественно монохромным.

## Типографика

SF Pro или системный аналог.

Рекомендуемые размеры:

- Главный заголовок: 30–34 pt, semibold.
- Заголовки секций: 18–20 pt, semibold.
- Имя клиента: 16–17 pt, semibold.
- Превью сообщения: 14–15 pt, regular.
- Время события: 12–13 pt.
- Названия фильтров: 13–14 pt, medium.
- Статус: 12–13 pt, medium.
- CTA: 15–16 pt, semibold.

Поддерживай Dynamic Type и увеличение текста.

## Отступы

- Горизонтальный padding: 20–24 pt.
- Вертикальные интервалы секций: 20–28 pt.
- Внутренний padding строк: 14–16 pt.
- Между иконкой источника и текстом: 12 pt.
- Радиус карточек: 16–20 pt.
- Радиус фильтров: pill.
- Высота строки обращения: зависит от содержания, ориентировочно 88–112 pt.
- Минимальная активная область: 44 × 44 pt.

Не создавай огромные карточки, из-за которых на мобильном экране видны только два обращения.

Inbox должен быть компактнее Today и удобнее для быстрого просмотра очереди.

# 09. ОБЛАСТЬ C — КРАТКИЕ ПОКАЗАТЕЛИ

Покажи три компактных показателя.

Используй демонстрационные значения исключительно для макета.

### Показатель 1

**6**

**«Без ответа»**

Значение: обращения, по которым подтверждено отсутствие ответа в доступной истории либо зафиксировано применимое рабочее состояние, требующее ответа.

### Показатель 2

**3**

**«Пропущенные»**

Значение: подтверждённые события пропущенных рабочих вызовов, для которых ещё требуется обработка.

### Показатель 3

**2**

**«Без ответственного»**

Показывать в командном представлении при наличии соответствующих прав.

Для личного пространства третий показатель заменить на:

**«Новые»**

Число новых необработанных обращений.

### Важные правила счётчиков

- Счётчики относятся к текущему рабочему пространству и действующему набору фильтров либо явно показывают, что это общая сводка.
- Не показывать ноль вместо «Нет данных», когда источник недоступен.
- Не считать одно обращение несколькими уникальными клиентами.
- Одно событие может входить в несколько разных категорий; это не означает арифметическую сумму уникальных лидов.
- Если пропущенный звонок уже получил подтверждённое последующее действие, он не должен бесконечно находиться в очереди необработанных звонков.
- Изменение фильтра должно предсказуемо менять показатели или явно оставлять их общей сводкой.
- Для больших значений допускаются сокращения вроде `99+`, если интерфейс даёт возможность увидеть точное число в полном списке.

При нажатии на показатель открывается соответствующий фильтр внутри Inbox.

# 10. ОБЛАСТЬ D — ПОИСК

Под показателями размести поисковую строку.

Placeholder:

**«Имя, телефон или сообщение»**

Слева — иконка поиска.

Справа — кнопка очистки, если введён текст.

Поиск должен работать по разрешённым индексированным данным:

- Имени или названию контакта.
- Нормализованному телефону.
- Идентификатору клиента.
- Доступному тексту сообщений.
- Доступному имени аккаунта источника.
- Номеру объекта или запроса, если событие с ним связано.

Не обещай полнотекстовый поиск по медиа, аудио и закрытым каналам без соответствующей реализации.

### Поведение поиска

- Поиск не создаёт новые клиентские записи.
- Ввод не требует обязательного нажатия Enter, если поддержан безопасный быстрый поиск.
- Для серверного поиска используй предсказуемую задержку обновления.
- Сохраняй контекст текущего рабочего пространства.
- Не ищи в чужих источниках без прав.
- Поддерживай ввод кириллицы и латиницы.
- Корректно ищи номера `+998` в разных форматах.
- Не раскрывай личные данные людей вне доступного пространства.
- При пустом результате покажи понятный Empty State.

### Пустой результат

Заголовок:

**«Ничего не найдено»**

Подпись:

«Проверьте запрос или измените фильтры».

Кнопка:

**«Сбросить фильтры»**

Если доступ запрещён, не подменяй ошибку доступа сообщением «Ничего не найдено».

# 11. БЫСТРЫЕ ФИЛЬТРЫ

Под поиском расположен горизонтальный ряд selectable chips.

Базовые значения:

**«Все» | «Без ответа» | «Пропущенные» | «Новые»**

В командном режиме дополнительно:

**«Без ответственного»**

В расширенном состоянии:

**«Фильтры»** с иконкой настройки.

### UI

Выбранный фильтр:
- Чёрный фон.
- Белый текст.
- Полное скругление.

Не выбран:
- Светло-серый фон.
- Тёмный текст.

### Поведение

- По умолчанию выбран «Все».
- Для быстрого фильтра используется один активный вариант одновременно.
- Расширенные фильтры могут комбинироваться с быстрым фильтром, если комбинация логически допустима.
- Активные расширенные ограничения должны быть видны через индикатор или краткую подпись.
- Пользователь может сбросить фильтры одним действием.
- Горизонтальная прокрутка chips допускается, но обязательные действия не должны скрываться без визуальной подсказки.
- При смене фильтра не сбрасывай пользовательский поисковый запрос без явного действия.

### Статус «Без ответа»

Включает только случаи с достаточным подтверждением согласно применимому правилу.

Если ответ не может быть надёжно определён, запись должна иметь статус «Требует проверки» и не смешиваться с доказанным отсутствием ответа.

Слева:

**«Обращения»**

Справа:

**«Сначала важные»**

По нажатию открыть небольшое меню сортировки.

Варианты:

- Сначала важные.
- Сначала новые.
- Сначала старые.
- По ближайшему сроку ответа.

### Сортировка по умолчанию

**«Сначала важные»**

Применять только объяснимые правила:

- Подтверждённая просрочка по действующему правилу.
- Подтверждённое пропущенное обращение, требующее обработки.
- Новое необработанное обращение.
- Обращение с назначенным ближайшим сроком ответа.
- Остальные в работе.

Внутри одного приоритета — стабильная сортировка по времени события.

Не использовать выдуманные AI-оценки вероятности сделки.

Если пользователь выбрал «Сначала новые», не продолжать скрыто поднимать старые карточки наверх без объяснения.

# 14. ГЛАВНАЯ МОДЕЛЬ ДАННЫХ ДЛЯ UX

Прежде чем рисовать список, различай четыре сущности.

## 1. Событие

Единичный факт:

- Входящий вызов.
- Пропущенный вызов.
- Полученное сообщение.
- Отправленное сообщение.
- Изменение статуса доставки.
- Ручная запись контакта.

## 2. Диалог / Thread

Последовательность событий в рамках одного подключённого канала и конкретного внешнего диалога.

Например, Telegram-переписка клиента с рабочим аккаунтом агентства.

## 3. Клиент / Contact

CRM-сущность человека или организации, которая может иметь несколько подтверждённых каналов связи.

## 4. Обращение / Lead

Рабочий запрос, требующий квалификации или дальнейшей обработки.

Один клиент может иметь несколько разных запросов.

### Главное правило

**Один телефонный вызов не равен одному новому клиенту. Один диалог не всегда равен одной новой сделке.**

Не объединять эти сущности без достаточных оснований.

Для основного списка Inbox рекомендуется использовать **один элемент на активный каналовый диалог или рабочее обращение**, а не отдельную строку для каждого сообщения.

Пропущенные вызовы из телефонии могут группироваться в рабочий поток по доступному номеру и источнику, но история отдельных звонков сохраняется.

Если пришли три сообщения подряд от одного и того же собеседника в одном канале, основной список обычно показывает один диалог с последним событием и индикатором новых сообщений.

Если один человек написал из Telegram и Instagram, эти два источника могут оставаться разными строками до подтверждённого объединения его контактов и с сохранением истории исходных каналов.

# 15. АНАТОМИЯ СТРОКИ ОБРАЩЕНИЯ

Каждая строка должна иметь единую структуру.

### Левая зона

- Аватар клиента либо нейтральный placeholder.
- Маленькая иконка источника.
- Дополнительная иконка типа события, если это важно.

### Центральная зона

Первая строка:

**Имя клиента или безопасный идентификатор.**

Вторая строка:

**Последнее сообщение или тип события.**

Третья строка:

**Статус обработки / назначенный сотрудник / следующее действие.**

### Правая зона

- Время последнего события.
- Маленький индикатор новых событий, если есть.
- Меню `…`, если для текущего представления предусмотрены контекстные действия.

Строка целиком нажимается и открывает соответствующий диалог или карточку обработки.

### Визуальная иерархия

Имя и рабочий контекст должны быть хорошо читаемыми.

Если диалог новый, допускается более насыщенный вес заголовка.

Нельзя полагаться только на жирность для передачи статуса.

Время события должно отображаться в формате:

- `10:42` — сегодня.
- `Вчера` — предыдущий день.
- `24 окт.` — в течение текущего года.
- `25.12.2025` — более старые события, если это необходимо для однозначности.

Дата, время и «вчера» вычисляются по часовому поясу рабочего пространства.

### Длинные тексты

В списке максимум 1–2 строки превью.

Не обрезать критичные предупреждения о проблемах доступа.

Полный текст доступен только при переходе к соответствующему диалогу, если он разрешён.

### Приватность

При настройке скрытия чувствительных данных вместо полного текста сообщения использовать:

**«Содержимое скрыто настройками приватности».**

При отсутствии прав:

**«Нет доступа к содержимому».**

# 17. СИСТЕМА СТАТУСОВ ОБРАЩЕНИЙ

Очень важно не смешивать статус диалога с состоянием прочтения, доставки и интеграции.

## Уровень A — Рабочий статус

Возможные значения:

**Новое**

Обращение ещё не принято в работу.

**Требует ответа**

По доступным данным требуется ответ или обратное действие.

**В работе**

Ответственный занимается обращением, дальнейший процесс ещё не завершён.

**Ожидаем клиента**

От агента выполнено подтверждённое действие, и дальнейшее продолжение зависит от ответа клиента.

**Требует проверки**

Информации недостаточно для достоверного определения следующего состояния.

**Закрыто**

Обращение завершено по зафиксированной причине.

## Уровень B — Просмотр в SuperApp

- Не просмотрено.
- Просмотрено.

Этот статус не равен прочтению сообщения в самом Telegram, WhatsApp или Instagram.

## Уровень C — Подтверждение исходящего сообщения

- Черновик.
- Отправка запрошена.
- Отправлено провайдером, если подтверждено.
- Доставлено, если подтверждено.
- Прочитано, если поддерживается и подтверждено.
- Ошибка отправки.
- Неизвестно.

## Уровень D — Подключение

- Подключено.
- Ограниченные разрешения.
- Задержка синхронизации.
- Соединение прервано.
- Не подключено.

### UX-правило

На строке Inbox показывай **один главный рабочий статус**, а не четыре конкурирующие цветные метки.

Остальные технические состояния отображаются по необходимости в деталях.

Например:

«Требует ответа» — главный статус.

«Telegram · 2 новых · 10:15» — метаданные.

«Статус отправки недоступен» — дополнительное пояснение при открытии.

# 18. БЫСТРЫЕ ДЕЙСТВИЯ НА СТРОКЕ

Пользователь должен уметь выполнять основные действия без длинной навигации.

Контекстное меню `…`:

- Открыть диалог.
- Открыть клиента.
- Перезвонить, если номер доступен.
- Ответить, если функция отправки поддерживается.
- Создать задачу.
- Назначить ответственного, если разрешено.
- Изменить статус.
- Закрыть обращение.
- Переместить в архив, если допускается.
- Сообщить о неверном совпадении контактов.

Не показывать все эти действия одновременно в самой строке.

### Свайпы

Допускаются быстрые свайп-действия, если они не нарушают привычную прокрутку списка.

Рекомендуемые варианты:

Свайп вправо:
- «В работу».

Свайп влево:
- «Ещё».

Не размещать необратимое удаление на лёгком жесте.

Все свайп-действия обязательно дублируются доступными кнопками или меню.

### Закрытие

При выборе «Закрыть» предложи короткий выбор причины:

- Вопрос решён.
- Клиент отказался.
- Нерелевантное обращение.
- Дубликат.
- Другое.

Необязательно требовать причину для каждого простого ручного действия, но для закрытия необработанного обращения причина важна для качества данных.

Не превращать архивирование в способ скрытого выполнения KPI.

# 20. ОБРАБОТКА ПРОПУЩЕННЫХ ЗВОНКОВ

Это один из наиболее важных сценариев SuperApp.

### Что показывать

- Известный клиент либо новый номер.
- Подключённый источник вызова.
- Время.
- Направление.
- Статус события.
- Ответственный.
- Последнее связанное рабочее действие, если оно доступно.

### Ключевой CTA

**«Перезвонить»**

Если используется системный набор номера:
- Открыть доступный механизм звонка.
- Не считать это подтверждением состоявшегося разговора.
- После возвращения предложить зафиксировать результат.

### Результат звонка

Локальный Bottom Sheet:

**«Чем закончился звонок?»**

Варианты:
- Связались.
- Клиент не ответил.
- Перезвонить позже.
- Номер недоступен.
- Не относится к работе.
- Другое.

Если звонок происходит через интегрированную АТС и результат подтверждается провайдером, учитывать его как системное событие.

Если агент звонит с обычной SIM без доступного подтверждения, результат отмечается вручную.

### Несколько пропущенных звонков

Если один клиент позвонил три раза подряд на один и тот же рабочий номер:
- Не создавать три одинаковых независимых клиентских карточки.
- В общем списке можно показать один активный элемент с указанием «3 пропущенных вызова».
- В истории сохранить все три факта с реальным временем.
- Приоритет можно повысить только на основании понятного правила.

### Скрытый номер

Текст:

**«Номер не определён»**

Не показывать кнопку перезвона.

Не создавать вымышленный контакт.

Если источник поддерживает дополнительные допустимые сведения о событии, показывать их отдельно.

# 21. ОБРАБОТКА СООБЩЕНИЙ

### Входящее сообщение

Поступившее событие связано с конкретным каналом.

Если канал передал:
- Текст — показать доступный фрагмент.
- Изображение — «Фото».
- Голосовое сообщение — «Голосовое сообщение».
- Документ — «Документ».
- Видео — «Видео».
- Неподдерживаемый тип — «Сообщение неподдерживаемого типа».

Не показывай транскрипцию аудио, если она действительно не создана на законных основаниях.

Не выдумывай содержание вложений.

### Ответ из Inbox

При технической возможности — перейти в соответствующий рабочий диалог.

Система должна учитывать:
- Право пользователя на ответ.
- Разрешения канала.
- Ограничения времени и условий отправки.
- Наличие актуальной авторизации.
- Возможность подтверждения отправки.
- Возможные расходы на сообщения.

Если ответ возможен только во внешнем приложении:
- Покажи соответствующее действие.
- Не считай открытие приложения фактом отправки.

### AI-подготовка ответа

Если доступен AI Copilot:
- Предложить черновик.
- Дать пользователю его проверить.
- Разрешить редактирование.
- Не подставлять ложные характеристики объектов.
- Не отправлять автоматически.
- Не использовать недоступную личную историю.

Пример действия:

**«Подготовить ответ»**

Не заменять им обычный способ ручного ответа.

# 22. СОПОСТАВЛЕНИЕ ОБРАЩЕНИЙ С КЛИЕНТАМИ

Это основа Client 360°.

### Известный клиент

Если идентификатор канала подтверждён:
- Привязать диалог к существующему клиенту.
- Показать имя и контекст.
- Не создавать новую карточку контакта.

### Новый контакт

Показывать:

**«Новый контакт»**

CTA:

**«Создать клиента»**

Но не требовать создания клиента до прочтения самого обращения.

### Возможное совпадение

Если система предполагает, что Telegram-аккаунт и телефонный номер принадлежат одному человеку:

Показывать:

**«Возможно, это существующий клиент»**

CTA:

**«Проверить совпадение»**

Не объединять автоматически на основании похожего имени или неполного совпадения данных.

### Несколько потенциальных клиентов

Если один номер содержится в нескольких CRM-карточках, показывать:

**«Найдено несколько контактов»**

CTA:

**«Выбрать клиента»**

Не выбирай случайно одного.

### Общие номера

Учитывай семейные, корпоративные и общие номера.

Один номер телефона не всегда однозначно идентифицирует человека.

### Ограничения каналов

Telegram, WhatsApp и Instagram могут предоставлять разные идентификаторы пользователей.

Нельзя предполагать, что Instagram-имя, Telegram username и номер телефона автоматически описывают одну личность.

# 23. НАЗНАЧЕНИЕ ОТВЕТСТВЕННОГО

В агентстве каждое рабочее обращение должно иметь понятного ответственного либо открытый статус назначения.

### Для руководителя

Возможность:

**«Назначить сотрудника»**

Bottom Sheet:

Заголовок:

**«Кому назначить обращение?»**

Список доступных сотрудников:
- Имя.
- Рабочая роль.
- Допустимый индикатор доступности, если реальные данные существуют.

Дополнительное действие:

**«Назначить себе»**

Кнопка:

**«Сохранить»**

### Для сотрудника

Если правила агентства позволяют брать свободные обращения:

**«Взять в работу»**

После нажатия:
- Выполнить серверное подтверждение.
- Назначить сотрудника.
- Обновить статус.
- Избежать двойного назначения.

### Конкурентное назначение

Если два агента одновременно нажали «Взять в работу»:
- Сервер определяет результат.
- Первый успешно подтвердивший назначение получает его в соответствии с бизнес-правилами.
- Второй видит:

**«Обращение уже назначено другому сотруднику»**

При этом пользователь может открыть доступный ему контекст или обратиться к руководителю.

### Переназначение

При изменении ответственного:
- Сохранить историю.
- Не удалять клиентские события.
- Уведомить затронутых сотрудников в рамках их прав.
- Обновить видимость в личной очереди.

# 24. РОЛЕВАЯ МОДЕЛЬ

## Роль A — Самостоятельный риэлтор

Показывать:
- Личные подключённые источники.
- Собственные обращения.
- Собственные задачи.
- Собственную историю клиентов.

Не показывать интерфейс распределения команды.

## Роль B — Риэлтор агентства

Показывать:
- Назначенные рабочие обращения.
- Разрешённые общие источники.
- Свои задачи.
- Доступные клиентские карточки.
- Возможность взять свободное обращение, если это разрешено.

Не показывать личные переписки других агентов.

## Роль C — Руководитель агентства

Показывать:
- «Мои / Команда».
- Доступные командные обращения.
- Заявки без ответственного.
- Сотрудников, которым назначены заявки.
- Подтверждённые просрочки по заданным правилам.
- Инструменты назначения и переназначения.

Не предоставлять автоматический доступ к частным мессенджерам сотрудников.

### Разграничение пространств

Личное пространство и пространство агентства — разные контексты доступа.

Переход между ними не должен незаметно переносить клиентскую историю или сообщения.

Соблюдай права доступа на уровне серверных запросов, а не только скрытием кнопок.

# 25. ПРАВИЛА SLA И ОБРАБОТКИ

В CRM можно настроить нормативы ответа, но нельзя выдавать их за универсальные факты.

Пример:

**«Обращение требует ответа по правилу вашей команды».**

Если агентство установило SLA 15 минут:
- Отслеживать дату и время получения доступного обращения.
- Учитывать установленный рабочий график, если это часть правила.
- Показывать реальную просрочку только при выполнении условий.

Если SLA не настроен:
- Не создавать выдуманную просрочку.
- Отображать новое обращение как требующее обработки без ложной метки «Просрочено».

### Состояния

**Новое**

Обращение не взято в работу.

**Ожидает ответа**

Ответ требуется согласно доступной истории и действующему правилу.

**Просрочено**

Известный установленный срок обработки прошёл, а требуемое действие не подтверждено.

**Требует проверки**

Данных недостаточно.

### Часовой пояс

Первоначально Asia/Tashkent, если рабочее пространство не настроено иначе.

Не допускать ошибок на границах дня, при смене часового пояса и получении задержанных событий.

# 26. СИНХРОНИЗАЦИЯ В РЕАЛЬНОМ ВРЕМЕНИ

Inbox должен ощущаться живым и актуальным.

### Новое событие

Когда поступает новый доступный звонок или сообщение:
- Обновить счётчики.
- Предложить показать новую запись.
- Не мешать пользователю читать текущий список.

Если пользователь находится в середине ленты, показывать компактное уведомление:

**«3 новых обращения»**

По нажатию:
- Перейти к верхней части списка.
- Показать новые события.

Не выполнять внезапную автоматическую прокрутку во время чтения.

### Обновление статусов

Если ответственный изменился с другого устройства:
- Обновить соответствующую строку.
- Сохранить понятный контекст.

Если обращение закрыто на другом устройстве:
- Показать актуальное состояние.
- Не разрешать сохранить устаревшее конфликтующее действие без проверки.

### Сохранение позиции

При появлении новых событий сохранять положение списка, пока пользователь сам не решит перейти к ним.

### Пагинация

Для длинной очереди использовать постраничную подгрузку или другой устойчивый механизм.

Не загружать одновременно тысячи диалогов в DOM.

Обязательно предусмотреть:
- Skeleton для следующей порции.
- Индикатор завершения списка.
- Обработку ошибок подгрузки.
- Сохранение активных фильтров.

# 27. ОТСУТСТВИЕ ДУБЛЕЙ

SuperApp не должен показывать одно и то же событие многократно.

### Повторный webhook

Если внешний провайдер отправил событие дважды, пользователь должен увидеть один логический факт.

### Несколько событий одного диалога

Группировать в пределах одного каналового thread, если источник подтверждает идентичность диалога.

### Разные каналы

Не объединять Telegram и WhatsApp только по совпадающему имени.

### Один контакт — несколько запросов

Не смешивать независимые клиентские запросы без подтверждения связи.

### Дубликаты CRM

Если обнаружены возможные дубли клиентов, предлагать проверку.

Не удалять источники и исходные события при объединении.

### Изменённые и удалённые сообщения

Если провайдер присылает события редактирования или удаления:
- Обновлять отображение в соответствии с фактически полученными данными и применимой политикой хранения.
- Не показывать удалённый текст как актуальный.
- Сохранять необходимую проверяемую историю действий в рамках правомерной обработки и хранения.

### Обновление фильтра

Не показывать белый экран.

### Загрузка новых обращений

Не сбрасывать уже просмотренную историю.

### Загрузка следующей страницы

Небольшой Skeleton внизу.

### Проверка подключения

Обновление статуса в соответствующем компоненте, а не блокировка всего Inbox.

- Подготовка черновика.
- Создание локальной заметки, если offline queue реализована.

# 32. ТЕХНИЧЕСКИЕ ОГРАНИЧЕНИЯ ИНТЕГРАЦИЙ

Этот раздел обязателен для реалистичного UX.

## Телефония

Поддерживаемые источники:

- Подключённая облачная АТС.
- Серверная телефония с доступными событиями.
- Допустимые нативные механизмы, если отдельно реализованы и разрешены.

Нельзя обещать, что веб-приложение автоматически получает полный журнал обычных звонков личной SIM-карты.

Android ограничивает доступ к журналу звонков, в том числе через правила Google Play. Для некоторых корпоративных CRM-сценариев предусмотрена отдельная процедура допуска; её существование не означает автоматического разрешения для нашего продукта.

На iPhone Caller ID и CallKit не являются универсальным API для выгрузки всей истории сотовых звонков в CRM.

## Telegram Business

Использовать только разрешённые события подключённого бизнес-бота.

Учитывать:
- Выбранные чаты.
- Права бота.
- Ограничения отправки сообщений.
- Изменение разрешений.
- Отключение бизнес-соединения.
- Ограничения доступности предыдущих сообщений.

Не показывать личные чаты, на которые нет прав.

## WhatsApp Business

Использовать официальный WhatsApp Business Platform.

Учитывать:
- Разрешённый бизнес-номер.
- Доступные webhook-события.
- Статусы отправки, если они предоставлены.
- Правила окон общения.
- Ограничения шаблонов.
- Возможные внешние расходы.
- Отсутствие полного доступа к любому личному WhatsApp-аккаунту.

Не отображать доставку и прочтение сообщения без достоверного подтверждения.

## Instagram

Использовать поддерживаемый профессиональный Instagram-аккаунт и официальные API Meta.

Учитывать:
- Необходимые разрешения.
- Ограничения инициирования переписки.
- Доступность событий Direct.
- Возможные ограничения старой истории.
- Статусы авторизации.
- Различия между Instagram Login и Facebook Login.

Не выдавай Instagram-аккаунт за подключённый, если разрешение на сообщения не получено.

## Принцип одинаковой визуальной модели

Даже если источники сильно отличаются технически, список обращений должен иметь единую визуальную систему.

Но нельзя стандартизировать данные путём выдумывания отсутствующих полей.

# 33. ЛОКАЛИЗАЦИЯ ДЛЯ УЗБЕКИСТАНА

Основной язык макета — русский.

Предусмотреть полноценную узбекскую локализацию.

Поддерживать:
- Узбекскую латиницу.
- Русскую кириллицу.
- Форматы телефонов +998.
- Местные имена и названия районов.
- Разные длины перевода.
- Валюты UZS и USD в будущем клиентском контексте.

Не перегружать Inbox деталями объектов.

Если нужен контекст:

**«Аренда · Чиланзар · До $500»**

или

**«Покупка · Юнусабад»**

Такие данные показываются только если они действительно записаны в CRM.

Не генерировать их на основании самого факта звонка.

# 34. ACCESSIBILITY

Обязательно поддерживать:

- VoiceOver.
- TalkBack.
- Dynamic Type.
- WCAG 2.2 AA для применимых веб-сценариев.
- Контрастность текста.
- Минимальные интерактивные области 44 × 44 pt.
- Полноценное управление клавиатурой.
- Видимый фокус.
- Корректную семантику заголовков и списков.
- Доступные названия иконок.
- Reduce Motion.

Любое свайп-действие должно быть доступно через обычное меню.

### Крупный текст

- Строки становятся выше.
- Подписи переносятся.
- Время не перекрывает имя клиента.
- Меню действий остаётся доступным.

# 37. MICROINTERACTIONS & MOTION

- Плавное изменение состояния chip.
- Аккуратное обновление списка.
- Отсутствие резкой прокрутки.

## Новое обращение

- Ненавязчивое появление индикатора новых событий.
- Без насильственного перемещения пользователя наверх.

- Короткая обратная связь.
- Обновление строки.
- Небольшое подтверждение результата.

- Короткое состояние сохранения.
- После подтверждения обновить ответственного.
- При конфликте показать понятную ошибку.

- Системная плавная анимация.
- Продолжительность ориентировочно 180–260 мс.
- Поддержка закрытия и возврата фокуса.

Необязательные перемещения отключаются.

Не использовать:
- Постоянную пульсацию.
- Автоматическое прыгание списка.
- Навязчивые звуки.
- Сложные 3D-переходы.
- Конфетти после обработки заявки.

### Основные KPI

**Capture Coverage**

Доля доступных событий, зарегистрированных из подключённых источников по сравнению с достоверными контрольными журналами.

**First Response Time**

Время между поступлением обращения и подтверждённым первым ответом.

**Unanswered Rate**

Доля обращений, у которых подтверждено отсутствие необходимого ответа.

**Missed Call Recovery Rate**

Доля подтверждённых пропущенных звонков, по которым выполнено обратное действие.

**Lead Assignment Time**

Время до назначения ответственного.

**Inbox Action Completion**

Доля обращений, для которых зафиксировано полезное действие.

**Data Confidence Rate**

Доля рабочих статусов, основанных на достаточных данных.

**Duplicate Event Rate**

Доля повторно доставленных внешних событий, корректно обработанных без пользовательских дублей.

### North Star Alignment

Вся работа Inbox должна поддерживать North Star Metric SuperApp:

**Подтверждённые рабочие возможности, по которым выполнено полезное действие.**

Не считать просмотр сообщения завершённым полезным действием.

Не считать открытие системного набора номера успешным звонком.

Не считать генерацию AI-черновика ответом клиенту.
