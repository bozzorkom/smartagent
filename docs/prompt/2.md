# 01. РОЛЬ ДИЗАЙНЕРА

Действуй как Principal Product Designer, Senior UX/UI Designer, Mobile UX Architect и эксперт по проектированию безопасной авторизации для современных SaaS-приложений.

Спроектируй **один законченный пользовательский сценарий «Регистрация и вход»**, включающий ввод телефонного номера, SMS-подтверждение, обработку ошибок и успешную авторизацию.

Это один номерной экран SuperApp — **№02**, но он содержит два основных состояния:

- Ввод номера телефона.
- Подтверждение одноразовым кодом.

Также спроектируй все необходимые состояния загрузки, ошибок, восстановления и возвращения пользователя.

Не разделяй эти состояния на разные номера экранов общей архитектуры.

**Не пиши программный код. Создай профессиональную UX/UI-спецификацию для Figma и последующей разработки.**

# 02. КОНТЕКСТ И ФИЛОСОФИЯ SUPERAPP

SuperApp — интеллектуальная рабочая система риэлтора, которая помогает не упускать клиентов, находить подходящие объекты и доводить рабочие возможности до сделок.

Первый продукт экосистемы — Lead Shield: контроль рабочих обращений из поддерживаемых телефонных и коммуникационных источников.

Дальнейшие направления продукта:

- Клиенты и CRM.
- Единый Inbox для рабочих обращений.
- Контроль пропущенных звонков и сообщений.
- AI Client Rescue.
- Today и следующие действия.
- Property Hub.
- Smart Match.
- Показы и сделки.
- Комиссии.
- Аналитика.
- Управление агентством.
- Подключаемые профессиональные модули.

Долгосрочная философия продукта — **«смартфон для бизнеса»**: пользователь получает единую базовую платформу и добавляет только необходимые инструменты.

Авторизация не должна заставлять человека сразу разбираться в этих возможностях.

**Задача экрана №02 — безопасно и максимально просто дать пользователю доступ к SuperApp.**

Целевые пользователи:

1. Частный риэлтор, работающий самостоятельно.
2. Риэлтор агентства недвижимости.
3. Владелец или руководитель агентства.

Все три аудитории проходят одинаковый простой вход. Их роль определяется позже, на экране №03 «Персонализация».

# 03. ЦЕЛЬ И ПСИХОЛОГИЯ ЭКРАНА

Ключевая пользовательская мысль:

**«Мне достаточно номера телефона, чтобы начать. Это быстро, понятно и безопасно».**

Основные цели:

- Минимизировать трение при первом входе.
- Убрать необходимость придумывать пароль.
- Объединить вход и создание аккаунта в один понятный процесс.
- Подтвердить владение указанным номером.
- Создать или восстановить пользовательскую сессию.
- Сохранить дальнейший путь пользователя.
- Объяснить, что подтверждение номера не даёт приложению доступа ко всем звонкам и контактам.

Не запрашивать:

- Имя и фамилию.
- Название агентства.
- Пароль.
- Адрес электронной почты.
- Должность.
- Паспортные данные.
- Геолокацию.
- Доступ к контактам.
- Доступ к телефонному журналу.
- Разрешение на уведомления.
- Разрешение на микрофон.

Эти сведения не нужны для первичной авторизации.

# 04. ОСНОВНОЕ UX-РЕШЕНИЕ

**Единый вход по телефонному номеру.**

Не показывай две большие вкладки «Регистрация» и «Вход».

Пользователь вводит номер и подтверждает одноразовый код.

После успешной проверки сервер самостоятельно определяет дальнейший маршрут:

- Новый пользователь → персонализация.
- Существующий пользователь с завершённой настройкой → его рабочее пространство.
- Пользователь с незавершённой настройкой → продолжение настройки.
- Пользователь с несколькими доступными рабочими пространствами → предусмотренный выбор пространства, если он действительно необходим.

На этапе ввода номера не раскрывать постороннему человеку, существует ли аккаунт с таким номером.

Не создавать новый аккаунт до успешного подтверждения телефона.

**Не добавлять обязательное поле пароля.**

# 06. STATE A — ОСНОВНОЙ ЭКРАН ВВОДА ТЕЛЕФОНА

## Верхняя часть

Слева:

Кнопка назад с минималистичной стрелкой.

Действие: вернуться к последнему слайду Intro, если авторизация была открыта оттуда.

Никакой кнопки «Пропустить» на этапе авторизации.

Причина: доступ к защищённой CRM требует установленной пользовательской сессии.

Верхняя часть должна быть практически пустой, чтобы пользователь сосредоточился на одном действии.

## Логотип

В верхней области контента показать компактный логотип или текстовую надпись:

**SuperApp**

Логотип монохромный, чёрный.

Не использовать тяжёлую заставку.

## Главный заголовок

**«Начните с номера телефона»**

## Подзаголовок

**«Отправим код подтверждения, чтобы вы могли войти или создать аккаунт».**

Текст должен быть коротким, спокойным и понятным.

Не использовать:

«Пройдите обязательную идентификацию».

«Авторизуйтесь через OTP».

«Создайте учётную запись с последующей верификацией».

Пользователь не обязан понимать технические термины.

## Поле телефона

Label:

**«Номер телефона»**

Состав поля:

Слева:
- Код страны `+998`.
- При необходимости небольшой флаг Узбекистана.
- Тонкий вертикальный разделитель.

Справа:
- Ввод девяти цифр национального номера.
- Placeholder: `90 123 45 67`.

Пример отображения полного номера:

**+998 90 123 45 67**

Код страны +998 выбран по умолчанию, поскольку продукт запускается в Узбекистане.

Для первого локального релиза допустимо поддерживать только узбекские номера, если такое продуктовое и техническое решение подтверждено. В этом случае код страны не должен выглядеть как работающий переключатель.

Если международные номера действительно поддерживаются сервером и SMS-провайдером, можно добавить выбор страны. Не создавать фиктивный список стран без работоспособной отправки SMS.

## Поведение поля

- Ввод только символов телефонного номера.
- При вставке очищать форматирующие пробелы, скобки и дефисы.
- Корректно обрабатывать номер, вставленный с `+998`.
- Не дублировать префикс `+998`.
- Форматировать номер на экране для удобства.
- Отправлять на сервер нормализованный международный номер.
- Не хранить пробелы как часть идентификатора.
- Использовать системную телефонную клавиатуру.
- Не изменять цифры пользователя незаметно.
- Не разрешать несколько ведущих плюсов.
- Не допускать двойной отправки.

Валидация должна учитывать актуальные правила нумерации и поддерживаемость отправки SMS, а не только визуальную маску.

Ошибка для неполного номера:

**«Введите номер телефона полностью».**

Ошибка для неподдерживаемого формата:

**«Проверьте номер телефона».**

Ошибка для номера, который сервис пока не поддерживает:

**«Пока не можем отправить код на этот номер».**

Не показывать красную ошибку, пока пользователь только начинает ввод.

## Основной CTA

**«Получить код»**

Чёрная кнопка на всю доступную ширину.

Состояния:
- Disabled — номер невалиден или неполон.
- Enabled — номер соответствует клиентской проверке.
- Loading — выполняется запрос к серверу.
- Error — запрос не выполнен.
- Success — получено подтверждение, что запрос принят SMS-сервисом.

При Loading использовать компактный spinner и текст:

**«Отправляем код…»**

Не показывать сообщение «Код отправлен» до подтверждения от серверного процесса отправки.

Даже после принятия SMS-провайдером нельзя гарантировать фактическую доставку сообщения.

## Юридический блок

Расположение — ниже основной кнопки.

Текст:

**«Продолжая, вы принимаете Условия использования и подтверждаете ознакомление с Политикой конфиденциальности».**

«Условия использования» и «Политика конфиденциальности» — отдельные интерактивные ссылки.

Использовать данную формулировку как дизайн-гипотезу, подлежащую юридической проверке.

Если правовая модель требует отдельного согласия на конкретную обработку данных, спроектируй отдельный понятный механизм получения такого согласия.

Согласие на рекламные сообщения никогда не должно быть автоматически объединено с обязательной авторизацией.

## Небольшая гарантия прозрачности

В самом низу, без отдельной яркой карточки:

Иконка щита.

Текст:

**«Номер используется для входа и защиты аккаунта. Доступ к звонкам и сообщениям настраивается отдельно».**

Это особенно важно для SuperApp, в котором позже предусмотрено подключение телефонии.

# 07. STATE B — ПОДТВЕРЖДЕНИЕ ТЕЛЕФОНА

После принятого запроса на отправку кода экран плавно переходит ко второму состоянию.

## Верхняя навигация

Кнопка назад.

Действие:
- Вернуться к вводу номера.
- Сохранить введённый номер.
- Не очищать его без необходимости.

## Заголовок

**«Подтвердите номер»**

## Подзаголовок

**«Введите код из SMS, отправленного на номер»**

Следующая строка:

**+998 90 ••• •• 67**

Маскировать номер для приватности при сохранении достаточного контекста.

Ниже:

**«Изменить номер»**

По нажатию пользователь возвращается к вводу телефона с сохранённым значением.

После изменения номера старую попытку подтверждения нельзя использовать для авторизации нового номера.

## Ввод одноразового кода

Рекомендуемая длина для проекта — **6 цифр**, при условии поддержки выбранной серверной системой.

Визуально использовать шесть одинаковых ячеек:

`□ □ □ □ □ □`

Каждая ячейка:
- Крупная цифра.
- Нейтральный фон.
- Радиус 12–16 pt.
- Активное состояние.
- Понятный фокус.

Технически UX должен допускать один логический ввод, визуально разделённый на шесть ячеек.

Это важно для:
- Доступности.
- Автозаполнения.
- Вставки полного кода.
- Корректной работы экранных дикторов.

Не создавать шесть независимых полей, которые ломают вставку кода или VoiceOver.

## Автозаполнение

Использовать системные механизмы автоматического предложения одноразового кода, если они доступны.

Для веб-версии предусмотреть стандартное автозаполнение OTP и прогрессивную поддержку WebOTP в совместимых браузерах.

На iOS использовать поддерживаемый механизм One-Time Code AutoFill.

Привязка SMS-кода к действительному домену приложения повышает устойчивость к фишингу.

Не предполагать, что автоматическое заполнение будет работать на всех устройствах и браузерах.

Ручной ввод должен оставаться полноценным способом подтверждения.

## Подтверждение кода

Основная кнопка:

**«Подтвердить и войти»**

При вводе полного шестизначного кода кнопка становится доступной.

Допускается автоматическое начало проверки после шестой цифры, но не создавай неконтролируемые повторные запросы.

Для базового проекта рекомендуется оставить понятную кнопку и предусмотреть быстрый ввод через AutoFill.

Состояние проверки:

**«Проверяем код…»**

При успехе сервер создаёт или возобновляет пользовательскую сессию.

# 08. SMS: ПРИМЕР ТЕКСТА

Пример SMS для дизайн-спецификации:

**«Код входа SuperApp: 123456. Никому не сообщайте этот код».**

Для доменно-привязанного автозаполнения формат должен соответствовать официальным требованиям соответствующей платформы и использовать фактический подтверждённый домен приложения.

Не указывай вымышленный домен SuperApp как действующий.

Код должен быть:
- Случайно сгенерирован.
- Одноразовый.
- Краткосрочный.
- Проверяемый сервером.
- Не записываемый открытым текстом в клиентскую аналитику.
- Недействительный после успешного применения.

Срок действия, число попыток и повторная отправка должны определяться серверной политикой.

Рекомендуемые значения для первого теста:
- Шесть цифр.
- Ориентировочно пять минут действия.
- Не более пяти неудачных попыток на одну попытку подтверждения.
- Повторная отправка не ранее чем через 60 секунд.

Это проектные значения, а не универсальные требования SMS-провайдера.

# 09. ПОВТОРНАЯ ОТПРАВКА SMS

Под полем OTP показать:

**«Не получили код?»**

Ниже:

**«Отправить повторно через 00:60»**

Используй корректный таймер, начиная с `01:00`, если установлен интервал 60 секунд.

Во время ожидания кнопка повторной отправки недоступна.

После окончания интервала:

**«Отправить код повторно»**

При нажатии:
- Сервер проверяет ограничения.
- Выполняет новую попытку отправки.
- Обновляет время ожидания.
- Показывает результат.

Если серверная политика делает предыдущий код недействительным, интерфейс должен явно сообщить:

**«Мы отправили новый код. Используйте последний полученный».**

Не допускать неограниченной отправки SMS.

При необходимости применять дополнительные защитные проверки, не усложняя стандартный пользовательский путь.

## Пользователь не получил SMS

После разумного ожидания показать ссылку:

**«Проблемы с получением кода?»**

Открыть компактный Bottom Sheet:

Заголовок:

**«Не приходит код?»**

Текст:

«Проверьте номер, связь и сообщения на телефоне. Иногда SMS приходит с задержкой».

Действия:

- «Проверить номер».
- «Отправить повторно», если доступно.
- «Связаться с поддержкой».

Не предлагать заведомо неработающие альтернативы, например WhatsApp OTP или звонок с кодом, если эти способы не реализованы и не подключены к провайдеру.

# 10. ЕДИНАЯ ЛОГИКА РЕГИСТРАЦИИ И ВХОДА

## Новый пользователь

1. Открывает SuperApp после Intro.
2. Вводит номер телефона.
3. Получает SMS.
4. Подтверждает код.
5. Сервер создаёт аккаунт и сессию.
6. Пользователь переходит к экрану №03 «Персонализация».

Не показывать промежуточные формы с паролем, именем или названием агентства.

## Существующий пользователь

1. Вводит ранее зарегистрированный номер.
2. Подтверждает SMS.
3. Сервер восстанавливает доступ.
4. Открывается последнее допустимое рабочее пространство или предусмотренный выбор пространства.

Не отправлять уже зарегистрированного пользователя на повторную регистрацию.

## Пользователь с незавершённым онбордингом

После входа восстановить сохранённый прогресс.

Если он завершил №03, но не настроил каналы №04, продолжить соответствующий этап либо применить принятые правила его пропуска.

Не принуждать заново проходить Intro.

## Пользователь с несколькими рабочими пространствами

После подтверждения номера использовать отдельный предусмотренный механизм выбора рабочего пространства.

Не считать факт владения телефоном разрешением на доступ к любому агентству, где такой номер встречается в клиентской базе.

## Пользователь с приглашением в агентство

Подтверждение номера само по себе не должно означать принятия приглашения.

Запросить подтверждение перехода или присоединения в предусмотренном сценарии.

Не раскрывать корпоративные данные до проверки необходимых прав.

---

# 11. STATE C — УСПЕШНАЯ АВТОРИЗАЦИЯ

После подтверждения кода показать краткую обратную связь.

Не создавать отдельную обязательную заставку на несколько секунд.

Допустимы:
- Небольшая галочка.
- Мягкий переход.
- Лёгкая тактильная обратная связь на поддерживаемом устройстве.

Текст:

**«Номер подтверждён»**

При необходимости:

**«Подготавливаем ваше пространство…»**

Переход должен происходить после фактического установления безопасной сессии, а не только после локальной анимации.

Не показывать успех, если серверная сессия не создана.

# 12. ПОЛНАЯ МАТРИЦА СОСТОЯНИЙ

Разработай отдельные варианты:

| Состояние | Что видит пользователь | Действие |
|---|---|---|
| Initial | Пустой номер, CTA недоступен | Ввести номер |
| Typing | Маска заполняется | Продолжить ввод |
| Invalid Phone | Ошибка формата | Исправить |
| Sending SMS | Индикатор отправки | Дождаться результата |
| SMS Accepted | Форма OTP | Ввести код |
| OTP Partial | Заполнена часть ячеек | Продолжить |
| OTP Complete | Код введён | Подтвердить |
| OTP Verifying | Проверка кода | Защита от повторной отправки |
| OTP Incorrect | «Неверный код. Попробуйте ещё раз» | Исправить |
| OTP Expired | «Срок действия кода истёк» | Запросить новый |
| Too Many Attempts | «Слишком много попыток. Попробуйте позже» | Следовать серверному ограничению |
| Resend Available | Кнопка повтора активна | Отправить повторно |
| Rate Limited | Показан доступный срок повторения | Подождать |
| Network Error | Ошибка соединения | Повторить |
| Provider Error | Временная проблема SMS-сервиса | Повторить позже |
| Session Creating | Создание сессии | Не дублировать процесс |
| Authentication Success | Успешное подтверждение | Перейти к маршруту |
| Existing User | Вход в текущий аккаунт | Открыть пространство |
| New User | Создание нового аккаунта | Перейти к персонализации |
| Returning User | Восстановление состояния | Продолжить |
| Blocked Account | Доступ ограничен по подтверждённой серверной политике | Поддержка и допустимое восстановление |

Для каждой ошибки нужны:
- Короткий человеческий текст.
- Понятное следующее действие.
- Сохранение безопасных данных формы.
- Возможность восстановления без повторного прохождения Intro.

Не раскрывать по публичным ошибкам, принадлежит ли номер существующему аккаунту.

# 13. БЕЗОПАСНОСТЬ И ЗАЩИТА АККАУНТА

Риэлторская CRM может содержать телефоны клиентов, коммерческие договорённости и данные сделок.

Поэтому даже простой SMS-вход должен проектироваться как часть серьёзной системы защиты.

Предусмотри:

- Серверную проверку кода.
- Ограничение попыток по номеру, устройству и другим допустимым сигналам.
- Защиту от SMS-фрода и массовых запросов.
- Недопущение повторного использования кода.
- Безопасную сессию.
- Защиту от повторного создания аккаунтов при гонках запросов.
- Понятный выход из аккаунта.
- Возможность управления активными сессиями в будущих настройках.
- Дополнительную проверку для критических операций.
- Механизм восстановления при потере доступа к номеру без возможности обхода проверки владения аккаунтом.

**Важное ограничение:** SMS-код не является самым сильным способом аутентификации из-за рисков SIM-swap, перевыпуска номера и перехвата сообщений.

На данном этапе SMS можно использовать как простой стартовый способ входа, но архитектура должна допускать последующее добавление более устойчивых факторов: passkeys, подтверждения с устройства или другой проверенной защиты.

Не выдавать SMS-подтверждение за абсолютную гарантию личности.

Не разрешать менять номер владельца аккаунта только на основании SMS на новый номер без надлежащей проверки уже существующей учётной записи.

# 14. ПЕРСОНАЛЬНЫЕ ДАННЫЕ И ЗАКОНОДАТЕЛЬСТВО УЗБЕКИСТАНА

Номер телефона — персональная информация, которую нужно защищать.

Спроектируй UX в соответствии с требованиями прозрачности, минимизации и законной обработки данных.

Предусмотри:
- Доступные юридические документы.
- Объяснение цели получения номера.
- Понятную политику хранения данных.
- В будущем — изменение телефона, экспорт и удаление аккаунта через предусмотренные процедуры.
- Отдельное управление маркетинговыми сообщениями.
- Ограничение доступа сотрудников поддержки.
- Неиспользование телефонного номера в открытых публичных идентификаторах.
- Маскирование номера в UI там, где полный номер не нужен.

В 2026 году законодательство Узбекистана о персональных данных изменилось. Поэтому местоположение серверов, регистрацию баз данных, передачу сведений SMS-провайдерам и возможную трансграничную обработку необходимо проверять с юристом перед запуском.

Не делай упрощённого вывода, что абсолютно все виды пользовательских данных всегда обязаны храниться исключительно на территории Узбекистана.

Не предлагай конкретного провайдера OTP как автоматически соответствующего всем местным требованиям.

# 15. РЕАЛЬНЫЕ ОГРАНИЧЕНИЯ SMS-ИНТЕГРАЦИИ

Дизайн должен быть независим от конкретного SMS-поставщика.

Сервис отправки кодов необходимо выбрать и проверить отдельно.

Учти:
- Возможные ограничения операторов связи Узбекистана.
- Доступность доставки на разные номерные диапазоны.
- Задержки сообщений.
- Роуминг.
- Стоимость отправки.
- Требования к имени отправителя.
- Ограничения по частоте.
- Возможные антифрод-проверки.
- Ошибки маршрутизации и временную недоступность.
- Тестовые номера для среды разработки.
- Недопустимость реальных SMS в автоматизированных тестах без контроля расходов.

Не показывай гарантированную доставку за конкретное число секунд, если такой показатель не подтверждён.

Не используй сторонний сервис для чтения входящих SMS пользователя.

Для веб-версии автоматическое получение OTP должно быть лишь удобным дополнением, а не обязательным условием входа.

# 16. КЛАВИАТУРА И MOBILE UX

## При вводе номера

- Открывать телефонную клавиатуру.
- Поддерживать вставку номера.
- Не вызывать текстовую автозамену.
- Не обрезать поле клавиатурой.
- Не заставлять пользователя вручную вводить `+998`, если префикс уже отображается.
- Позволять исправить любую цифру.
- При возвращении с OTP сохранять номер.

## При вводе кода

- Использовать цифровую клавиатуру.
- Поддерживать вставку всего кода.
- Корректно распознавать удаление цифры.
- Не перемещать фокус непредсказуемо.
- Давать пользователю прочитать ошибки.
- Не скрывать таймер повторной отправки.
- Не блокировать экран из-за отсутствия AutoFill.

## Работа со sticky CTA

На обычном экране телефонного ввода CTA может находиться в нижней части доступной области, если это не создаёт слишком больших расстояний между полем и действием.

Когда открыта клавиатура:
- CTA остаётся достижимой.
- Не перекрывает содержимое.
- Не прыгает из-за пересчёта высоты viewport.
- При недостатке места допускается прокрутка.

Не применять фиксирование кнопки поверх системной клавиатуры без адаптации под safe areas и Visual Viewport.

# 17. ANIMATION & MICROINTERACTIONS

Стиль — сдержанный, дорогой, системный.

## Появление экрана

- Плавное появление заголовка.
- Незаметное проявление основного поля.
- Без длительных анимационных заставок.

## Фокус на поле

- Мягкое изменение границы.
- Отсутствие сильного свечения.
- Не менять размеры карточки.

## Активация кнопки

- Короткий переход из disabled в enabled.
- Без резкого увеличения.

## Переход к OTP

- Плавная смена заголовка и формы.
- Ориентир длительности: 180–260 мс.
- Не блокировать ручной ввод, пока проигрывается анимация.

## Успех

- Сдержанная галочка.
- Лёгкий haptic feedback, если поддерживается.
- Переход без искусственной задержки.

## Ошибка

- Встроенное сообщение под соответствующим элементом.
- Вертикальные сдвиги должны быть минимальными.
- Не использовать агрессивное встряхивание всей страницы.

## Reduce Motion

- Уважать системную настройку.
- Полностью отключать необязательные перемещения.
- Сохранять обратную связь через текст и изменение состояния.

# 22. UX-АНАЛИТИКА

Предусмотри события:

- `auth_screen_viewed`
- `phone_input_started`
- `phone_validation_failed`
- `otp_request_started`
- `otp_request_accepted`
- `otp_request_failed`
- `otp_screen_viewed`
- `otp_autofill_used`
- `otp_verification_started`
- `otp_verification_failed`
- `otp_resend_requested`
- `auth_completed`
- `auth_abandoned`
- `auth_session_restored`

Ключевые KPI:

**1. Phone-to-OTP Conversion**

Доля пользователей, успешно запросивших код после открытия формы.

**2. OTP Completion Rate**

Доля пользователей, подтвердивших телефон среди тех, кто начал подтверждение.

**3. Authentication Completion Rate**

Доля пользователей, успешно завершивших авторизацию.

**4. Median Time to Authenticate**

Медианное время полного прохождения.

**5. OTP Resend Rate**

Доля попыток с повторной отправкой.

**6. SMS Delivery Performance**

Фактические показатели доставки, если провайдер предоставляет достоверный статус доставки.

**7. Authentication Cost**

Средняя стоимость SMS и защитных проверок на одну успешную авторизацию.

**8. Post-Authentication Activation**

Доля новых пользователей, дошедших до персонализации и первого полезного действия.

Не отправлять в обычные аналитические события:
- Полный номер телефона.
- OTP-код.
- Секреты сессии.
- Токены авторизации.
- Содержимое SMS.
