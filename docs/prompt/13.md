# 02. ФИЛОСОФИЯ SUPERAPP

SuperApp — интеллектуальная рабочая система риэлтора, которая помогает не упускать клиентов, находить подходящие объекты и доводить рабочие возможности до сделок.

Философия продукта — **«смартфон для бизнеса»**.

Пользователь получает базовую систему и самостоятельно подключает нужные профессиональные модули.

Например:

- CRM / Клиенты.
- Inbox / Обращения.
- Lead Shield.
- Client 360°.
- Tasks / Follow-up.
- Property Hub.
- Smart Match.
- Showing Manager.
- Deal Management.
- Commission Tracking.
- Analytics.
- AI Copilot.

Модули должны оставаться относительно независимыми.

**База клиентов — фундамент платформы, а не сложная CRM с сотнями обязательных полей.**

Она должна быть полезна даже без подключённых мессенджеров, AI, Smart Match и телефонии.

Риэлтор может создать клиента вручную, сохранить его запрос, добавить задачу и продолжать работу.

# 03. ГЛАВНАЯ UX-ЦЕЛЬ

После открытия базы клиентов пользователь за 3–5 секунд должен понять:

1. Сколько клиентов доступно в выбранном рабочем пространстве.
2. Как найти конкретного человека.
3. У каких клиентов есть незавершённые рабочие действия.
4. Какие клиенты появились недавно.
5. Кто не имеет следующего запланированного шага.
6. Как открыть контакт.
7. Как быстро продолжить работу.

Главная эмоция:

**«Все мои рабочие клиенты организованы. Я быстро нахожу нужного человека и понимаю, что делать дальше».**

В отличие от обычной телефонной книги, экран должен давать минимально необходимый рабочий контекст.

В отличие от Inbox, он должен показывать клиентов, а не поток сообщений.

В отличие от Client 360°, он должен оставаться компактным списком, а не подробной историей одного человека.

# 04. РАЗДЕЛЕНИЕ ОСНОВНЫХ СУЩНОСТЕЙ

Прежде чем создавать интерфейс, различай:

## Contact / Клиент

Человек или организация, с которыми ведётся работа.

Один контакт может иметь несколько телефонов, аккаунтов и запросов.

## Lead / Обращение

Конкретное входящее обращение или рабочая возможность.

Один клиент может обратиться многократно.

## Request / Запрос

Потребность в недвижимости.

Например:
- Покупка квартиры.
- Аренда офиса.
- Продажа собственного дома.

## Conversation / Диалог

Рабочая переписка в отдельном подключённом канале.

## Interaction / Взаимодействие

Звонок, сообщение, заметка или другое событие.

## Task / Задача

Следующее действие с ответственным и сроком.

## Property / Объект

Недвижимость, которую клиент предлагает либо рассматривает.

### Главный принцип

**Одна карточка клиента в списке не равна одной заявке, одному телефонному номеру или одному мессенджеру.**

Пример:

Клиент «Мадина К.» может иметь:
- Один подтверждённо связанный телефон.
- Telegram Business-диалог.
- Два активных запроса.
- Три предложенных объекта.
- Одну запланированную задачу.
- Несколько звонков.

В базе клиентов она должна отображаться **одной CRM-карточкой**, если все связи действительно подтверждены.

Не объединяй разных людей только потому, что у них одинаковые имена.

# 05. ГЛАВНОЕ ПРОДУКТОВОЕ РЕШЕНИЕ

Это **не таблица Excel**.

Это **action-oriented клиентский реестр**.

Каждый элемент списка показывает:

**Кто это?**

**С чем работает?**

**Что известно о последнем взаимодействии?**

**Есть ли следующий шаг?**

**Как продолжить работу?**

Не надо показывать в списке:
- Паспортные данные.
- Полную историю сообщений.
- Все внутренние заметки.
- Все объекты клиента.
- Множество аналитических показателей.
- Технические идентификаторы.
- Служебные поля интеграций.

Эти данные относятся к Client 360° и другим специализированным сценариям.

## Цвета

Secondary Text: #737373

Border: #E8E8E8

Семантические цвета:
- Сдержанный красный — реальная просрочка или ошибка.
- Янтарный — предупреждение или необходимость проверки.
- Зелёный — подтверждённое завершение.

Не раскрашивай клиентов по «температуре» без прозрачных правил.

Не используй большие яркие градиенты, тяжёлые тени и декоративные 3D-элементы.

## Типографика

SF Pro или качественный системный аналог.

- Главный заголовок: 30–34 pt, semibold.
- Заголовок секции: 18–20 pt.
- Имя клиента: 16–17 pt, semibold.
- Рабочий контекст: 13–15 pt.
- Следующее действие: 13–14 pt.
- Вторичные метаданные: 12–13 pt.
- Название фильтра: 13–14 pt.
- CTA: 15–17 pt.

## Размеры

- Горизонтальный padding: 20–24 pt.
- Отступы между секциями: 20–28 pt.
- Отступы между строками: 0–8 pt, в зависимости от системы разделителей.
- Высота строки клиента: ориентировочно 88–112 pt.
- Радиус карточек: 16–20 pt.
- Радиус chips: pill.
- Минимальная область нажатия: 44 × 44 pt.

Предпочитай **компактные строки с тонкими разделителями или очень светлыми поверхностями**.

Не делай каждую запись огромной карточкой с четырьмя кнопками.

# 09. РАБОЧИЕ ПРОСТРАНСТВА

SuperApp поддерживает личный и агентский контекст.

### Самостоятельный риэлтор

По умолчанию используется личная CRM.

Не показывай ненужные переключатели команды.

### Риэлтор агентства

Показывать только доступное агентское представление и другие разрешённые пространства.

### Руководитель

Если есть права:

**«Мои» / «Команда»**

Компактный segmented control.

### Пользователь в нескольких пространствах

В Header показывать действующее пространство:

**«Агентство»**

или:

**«Личное пространство»**

Выпадающий список доступных пространств — только если переключение действительно поддерживается.

### Главное правило

**Смена рабочего пространства не означает копирование клиентов между пространствами.**

При переключении:
- Изменяются доступные клиенты.
- Пересчитываются счётчики.
- Обновляются фильтры.
- Проверяются права.
- Личные данные предыдущего пространства не должны оставаться видимыми.

Для командного режима «Все» означает все контакты, доступные по текущим правам, а не все записи, существующие на сервере.

# 10. ОБЛАСТЬ B — КРАТКАЯ СВОДКА

Не более трёх компактных показателей.

Для демонстрационного макета:

**128 — Клиентов**

**6 — Требуют внимания**

**3 — Новые**

### Семантика

**Клиентов**

Количество доступных CRM-карточек в текущем пространстве и области видимости.

**Требуют внимания**

Количество уникальных доступных клиентов, имеющих хотя бы одно соответствующее открытое действие или подтверждённую причину внимания.

**Новые**

Контакты, созданные за явно установленный период, например последние 7 дней.

Не путать недавно созданного клиента с впервые поступившим сообщением.

### Правила

- Все значения относятся к конкретной области доступа.
- Один клиент учитывается один раз в каждом показателе.
- Показатели не обязаны суммироваться.
- Если данные недоступны, показать состояние «Нет данных», а не ноль.
- Если включён фильтр, явно определить: сводка общая для области доступа или пересчитана по текущему фильтру.
- При изменении рабочего пространства значения должны обновляться согласованно.

Не использовать KPI «Потерянные клиенты» по одному признаку отсутствия общения.

# 11. ОБЛАСТЬ C — ПОИСК

Поиск — одна из главных функций экрана.

Используй крупную светлую строку сразу под сводкой.

### Placeholder

**«Имя, телефон или клиент»**

Можно использовать более краткое:

**«Найти клиента»**

Выбери один вариант для финальной дизайн-системы.

### Иконки

Слева — поиск.

Справа — очистка, если есть текст.

### Доступные поля поиска

- Имя.
- Фамилия.
- Название организации.
- Нормализованный телефон.
- CRM ID, если пользователь использует такие номера.
- Подтверждённый разрешённый username канала.
- Рабочие теги.
- Доступный краткий контекст запроса, если соответствующий индекс действительно реализован.

### Форматы телефонов

Поддерживать номера Узбекистана:
- +998 90 123 45 67.
- +998901234567.
- 90 123 45 67, если регион поиска однозначно определён.

Нормализовать ввод, не теряя исходное отображаемое значение.

Для международных контактов учитывать поддерживаемые страны.

### Имена

Поддерживать:
- Кириллицу.
- Узбекскую латиницу.
- Регистр.
- Пробелы.
- Разные порядки имени и фамилии.
- Частичное совпадение.

### Неоднозначная транслитерация

Допускается дополнительный поиск похожих написаний, но нельзя считать такие совпадения доказательством идентичности людей.

### Скорость

Поиск должен ощущаться быстрым.

Показывай локальную загрузку при серверном запросе.

Не блокируй весь список из-за каждого символа.

# 13. ОБЛАСТЬ D — БЫСТРЫЕ СЕГМЕНТЫ

Под поиском размести горизонтальные chips:

**«Все» | «Новые» | «Требуют внимания» | «Без следующего шага» | «Архив»**

### Поведение

- По умолчанию выбран «Все».
- Один сегмент активен одновременно.
- Активный chip — чёрный.
- Неактивный — светло-серый.
- Выбранный сегмент сохраняется при возврате из Client 360°, если это уместно.
- Горизонтальная прокрутка допускается.
- При изменении сегмента сохранять поисковый запрос, если их комбинация допустима.
- Если выбор приводит к пустой выдаче, показать ясный Empty State.

### Важно

Сегменты должны иметь понятную логику данных.

Не создавать декоративные категории:
- «Самые горячие».
- «Потенциал миллион».
- «Почти потерян».
- «Гарантированная сделка».

Без достоверной модели и прозрачных критериев.

# 14. СЕГМЕНТ «ВСЕ»

Показывать все доступные активные CRM-карточки в текущем пространстве, исключая архив, если это определено как правило продукта.

### Рекомендуемый стандарт

«Все» = все неархивные доступные контакты.

«Архив» = отдельный сегмент.

### Сортировка по умолчанию

**«Последняя активность»**

Использовать фактическую дату последнего разрешённого значимого взаимодействия.

Если последняя активность неизвестна, не выдумывать дату.

### Альтернатива

Для пользователя, ориентированного на ежедневную работу, можно сохранять выбранную сортировку.

Не меняй её незаметно после каждого входа.

---

# 15. СЕГМЕНТ «НОВЫЕ»

Определение:

Контакты, созданные в CRM за выбранный период.

Рекомендуемый начальный период:

**Последние 7 дней**

Дополнительное пояснение:

**«Клиенты, добавленные за последние 7 дней»**

### Важно

Новый клиент и новое сообщение — разные вещи.

Если существующий контакт написал сегодня, он не становится новым CRM-клиентом.

Если пользователь создал нового клиента вручную, он может войти в этот сегмент, даже если не было ни одного сообщения.

### Период

Может быть изменён в расширенных фильтрах.

Не используй один фиксированный период для всех сегментов без возможности понимания логики.

# 16. СЕГМЕНТ «ТРЕБУЮТ ВНИМАНИЯ»

Это главный рабочий сегмент CRM.

Он не должен дублировать всю очередь Lead Shield.

### Возможные основания

Клиент имеет:
- Подтверждённое необработанное рабочее обращение.
- Просроченную задачу.
- Следующий шаг, требующий выполнения сегодня.
- Неподтверждённый результат, который нужно проверить.
- Другую явно установленную рабочую причину внимания.

### Важное правило

Сегмент основан на доступных рабочих событиях и задачах.

Не использовать исключительно длительное отсутствие сообщений как доказательство, что клиенту срочно нужно писать.

### В карточке

Показывать одну основную причину:

**«Перезвонить сегодня, 17:00»**

или:

**«Есть обращение без ответа»**

или:

**«Требуется проверить результат»**

### Если причин несколько

Показывать главную и маленькую подпись:

**«Ещё 2 действия»**

Ссылка ведёт к разрешённому контексту Client 360° или задач.

### Если источник отключён

Не показывать клиенту статус «Всё обработано» только потому, что события перестали приходить.

# 17. СЕГМЕНТ «БЕЗ СЛЕДУЮЩЕГО ШАГА»

Определение:

Доступные активные клиенты с актуальными рабочими запросами, у которых нет открытой задачи или другого явно определённого следующего действия.

### Почему важно

Клиент может существовать в CRM, но риэлтор не знает, что делать дальше.

### Карточка

Статус:

**«Следующее действие не назначено»**

CTA через меню:

**«Создать задачу»**

### Исключения

Не обязательно включать:
- Архивных клиентов.
- Клиентов без активных запросов.
- Контакты, с которыми запрещены дальнейшие коммуникации.
- Клиентов, уже находящихся в другом завершённом процессе.
- Недоступные контакты без права создания задач.

Правила должны быть прозрачными и настраиваемыми в продукте.

### Не допускай

Автоматической отправки сообщений всем клиентам сегмента.

Отсутствие задачи не означает разрешение на массовую рассылку.

# 18. СЕГМЕНТ «АРХИВ»

Показывать архивированные контакты.

### Визуальная логика

Нейтральный внешний вид.

Подпись:

**«В архиве»**

### Возможные действия

- «Открыть клиента».
- «Восстановить», если есть права.
- «История изменений», если доступна.
- «Удалить», только согласно правилам хранения и полномочий.

### Главное

Архив не равен удалению.

Не удалять историю звонков, сообщений, объектов или сделок при обычном архивировании клиента.

Не скрывать связанные незавершённые обязательства без проверки.

Если архивируемый клиент имеет активную задачу, предупреждать о последствиях или предлагать разрешить её.

# 19. ОБЛАСТЬ E — РАСШИРЕННЫЕ ФИЛЬТРЫ

- Дата неизвестна.

Не считать отсутствие данных равнозначным отсутствию общения.

### Секция 9 — Задачи

- Есть открытые.
- Есть просроченные.
- Без следующего действия.
- Есть запланированный контакт.

Например:
- Инвестор.
- Повторный клиент.
- Рекомендация.
- Коммерческая недвижимость.

# 24. CRM-СТАТУС КЛИЕНТА

Разработай простую систему статусов контакта.

### Новый

Контакт добавлен в CRM, а работа ещё находится на первоначальном этапе.

### Активный

Есть актуальный рабочий процесс или активный запрос.

### Без активных запросов

Контакт существует, но текущих открытых запросов нет.

### Архив

Контакт выведен из активного списка.

### Требует уточнения

Недостаточно данных для выбранного рабочего сценария.

### Не используй

- Автоматически «Потерян».
- «Гарантированная сделка».
- «Ненадёжный».
- «Плохой клиент».
- «VIP» по выдуманному доходу.

Если агентству нужны пользовательские теги приоритета, они должны быть явно определены и контролироваться пользователями.

### Очень важно

Статус CRM-контакта не равен:
- Статусу отдельного обращения.
- Этапу сделки.
- Подтверждённости доставки сообщения.
- Выполнению задачи.
- Подтверждённому согласию клиента.

### Минимальная валидация

Сохранение нового клиента допускается, когда есть достаточный идентификатор для рабочей CRM.

Не создавать пустую карточку без каких-либо сведений.

Если известен только внешний идентификатор подключённого канала, он может использоваться как техническая связь при наличии соответствующих прав и источника.

Если данных недостаточно, сохранить исходное обращение в Inbox/Lead без создания искусственной личности.

### Успех

**«Клиент добавлен»**

### После сохранения

Открыть Client 360° либо вернуть к списку с выделением нового клиента, согласно исходному сценарию.

Не запрещать создавать новую заявку при существующем контакте.

Не перезаписывать старые запросы автоматически.

### После сохранения

Клиент остаётся одной CRM-сущностью.

Количество связанных запросов увеличивается при действительном создании нового запроса.

# 33. ИМПОРТ КОНТАКТОВ

Если импорт включён в продукт, предусмотри локальную точку входа.

**«Импортировать клиентов»**

### Источники, если реально поддерживаются

- CSV-файл.
- Поддерживаемая CRM-интеграция.
- Системные контакты только через допустимый механизм с отдельным разрешением.

### Не обещать

- Автоматическое чтение всех контактов iPhone обычным Next.js-приложением.
- Скрытый импорт адресной книги.
- Копирование всей базы Telegram или WhatsApp.
- Автоматическое чтение телефонной книги сотрудников агентства.

Показать короткий предварительный просмотр:

**«Найдено 120 строк»**

**«Возможных совпадений: 8»**

Только после реального анализа файла.

- Формат номеров.
- Кодировку кириллицы и латиницы.
- Пустые строки.
- Повторные записи.
- Имена.
- Разделение колонок.
- Доступное рабочее пространство.
- Права пользователя.
- Наличие надлежащих оснований для обработки данных.

### CTA

**«Проверить перед импортом»**

Не импортировать тысячи клиентов без предварительного просмотра и понятного подтверждения.

### После импорта

Показывать реальный отчёт:
- Создано.
- Связано с существующими.
- Пропущено.
- Требует проверки.
- Ошибки.

# 34. МАССОВЫЕ ДЕЙСТВИЯ

После включения режима выбора:
- Checkbox у доступных строк.
- Количество выбранных.
- Панель допустимых действий.

### Разрешённые примеры

- «Назначить ответственного».
- «Добавить тег».
- «Убрать тег».
- «В архив», при наличии прав.
- «Экспорт», если разрешён.

### Опасные действия

Не делать доступным одним лёгким нажатием:
- «Удалить всех».
- «Отметить всех обработанными».
- «Отправить сообщение всем».
- «Объединить всех».

Массовая отправка сообщений — отдельный регулируемый и технически ограниченный продуктовый сценарий, не часть обычного управления контактами.

### Подтверждение

Если пользователь архивирует несколько записей:

**«Переместить 5 клиентов в архив?»**

Показывать число выбранных записей из реального состояния.

### Важное правило

Массовые операции должны повторно проверять права на сервере для каждого контакта.

Если часть элементов недоступна, показать честный частичный результат.

# 37. УДАЛЕНИЕ И ЭКСПОРТ

Это чувствительные функции.

### Удаление

Не размещать заметную красную кнопку в каждой строке.

Удаление требует:
- Соответствующей роли.
- Проверки связей.
- Подтверждения.
- Соблюдения сроков хранения.
- Учёта обязанностей по хранению связанных документов и событий.

### Важное различие

Удаление CRM-карточки не означает автоматического удаления внешних сообщений Telegram, WhatsApp или Instagram.

### Экспорт

Если реализован:
- Только разрешённая область данных.
- Явный формат.
- Учет прав.
- Журнал операций.
- Безопасный канал получения.
- Обоснованное ограничение массового извлечения данных.

### Необходимо предотвратить

Обычный сотрудник не должен получить всю агентскую базу через экспорт или поисковые запросы, если у него нет такого разрешения.

# 38. СТАТУСЫ ПОДКЛЮЧЁННЫХ КАНАЛОВ

База клиентов не должна зависеть от работоспособности мессенджера.

### Если Telegram отключён

Клиент сохраняется в CRM.

Связанный канал может иметь статус:

**«Telegram требует переподключения»**

Но сама клиентская карточка не исчезает.

### Если WhatsApp недоступен

Быстрое действие «Написать» не должно обещать встроенную отправку.

### Если Instagram не передал историю

Не показывать фиктивную последнюю переписку.

### Если облачная АТС отключилась

Ранее разрешённая сохранённая CRM-информация может оставаться доступной в рамках политики хранения.

Новые рабочие события не следует считать поступающими.

### Главное правило

**Контакт CRM и его внешний коммуникационный канал — разные сущности с разными состояниями.**

# 39. ПОСЛЕДНИЙ КОНТАКТ И АКТИВНОСТЬ

В строке списка часто полезно показать последнее взаимодействие.

Но важно правильно определить, что именно известно.

### Возможные источники

- Подтверждённое сообщение.
- Подтверждённый вызов.
- Ручная рабочая заметка.
- Зафиксированная задача.
- Подтверждённый показ, если модуль есть.

### Различай

**«Последнее сообщение»**

**«Последний звонок»**

**«Последняя рабочая активность»**

Это не одно и то же.

### Пример

«Последнее сообщение: вчера».

Если это подтверждено.

### Если событие отсутствует

**«История контактов недоступна»**

Или не показывай эту строку, если она не нужна.

### Важно

Создание CRM-карточки не доказывает, что клиенту звонили.

Открытие профиля не является клиентским взаимодействием.

# 40. ПРИОРИТИЗАЦИЯ БЕЗ ЛОЖНЫХ AI-ОЦЕНОК

CRM может помогать выделять клиентов, которым требуется внимание.

Но нельзя выдавать предположения за факты.

### Допустимые основания

- Просроченная задача.
- Запланированный звонок сегодня.
- Подтверждённое обращение без ответа.
- Новый запрос без ответственного.
- Действие, требующее проверки.

### Пример статуса

**«Нужно перезвонить»**

### Нежелательные статусы

- «Клиент на грани ухода».
- «Почти потерян».
- «Вероятность сделки 98%».
- «Клиент готов купить прямо сейчас».

Без обоснованной системы, подтверждённых данных и прозрачной интерпретации.

### Если AI Copilot подключён

Можно предложить:

**«SuperApp заметил незавершённое действие»**

По нажатию:

**«Почему это показано?»**

С объяснением на основе конкретной задачи или события.

AI не должен автоматически менять статус клиента или создавать задачу без допустимого правила и подтверждения.

# 42. ОБНОВЛЕНИЯ В РЕАЛЬНОМ ВРЕМЕНИ

Если пользователь имеет право его видеть:
- Обновить счётчики.
- Предложить обновление списка.
- Не нарушать текущую прокрутку.

### Новое событие от клиента

Если контакт подтверждён:
- Обновить последнюю активность.
- Обновить рабочий индикатор.
- Сохранить связь с нужным клиентом.

### Если пришло неизвестное сообщение

Не создавать автоматически новую подтверждённую клиентскую личность без достаточного основания.

Событие может сначала появиться в Inbox.

### Если клиент объединён с другим

Список должен:
- Убрать подтверждённый дубль согласно серверному состоянию.
- Сохранить корректную навигацию.
- Не открыть неожиданно неправильную карточку.

# 44. ПРАВА ДОСТУПА

## A — Частный риэлтор

Может:
- Видеть своих клиентов.
- Создавать.
- Редактировать.
- Архивировать.
- Искать.
- Сегментировать.
- Добавлять заявки и задачи.

В соответствии с правами конкретного пространства.

## Б — Сотрудник агентства

Может:
- Видеть назначенных клиентов.
- Просматривать разрешённые командные контакты.
- Создавать клиентов, если это разрешено.
- Редактировать назначенных клиентов в пределах прав.
- Открывать допустимый Client 360°.
- Создавать заявки и задачи.

Не может:
- Видеть скрытые личные контакты коллег.
- Массово экспортировать чужую базу без разрешения.
- Переносить клиентов между агентствами произвольно.

## В — Руководитель агентства

Может:
- Переключать разрешённое представление «Мои / Команда».
- Назначать ответственных.
- Просматривать доступную командную базу.
- Проверять дубли.
- Управлять сегментами при наличии прав.
- Использовать разрешённые административные действия.

Не получает автоматически доступ к личным мессенджерам сотрудников.

## Г — Пользователь без доступа

Показывать:

**«Доступ к клиентской базе ограничен»**

Подпись:

«У вас нет разрешения на просмотр этих контактов».

CTA:

**«Вернуться»**

### Техническое правило

Права проверяются сервером.

Скрытие кнопки в интерфейсе не является полноценной защитой данных.

# 45. СМЕНА РАБОЧЕГО ПРОСТРАНСТВА

Пользователь может работать самостоятельно и одновременно состоять в агентстве.

### При переключении

Показать новый контекст.

Очистить недопустимые результаты предыдущего поиска и кэша.

Сохранить фильтры только если они логически применимы к новому пространству.

### Если открыт Bottom Sheet редактирования

Не переключать пространство с несохранёнными данными без понятного подтверждения.

### Если клиент существует в двух пространствах

Не считать его общей CRM-карточкой автоматически.

Разные организации могут иметь отдельные правомерно созданные клиентские записи.

### Если пользователь хочет перенести контакт

Это отдельный контролируемый сценарий с правами, основаниями и подтверждением.

Не реализовывать такой перенос через обычное перетаскивание строки.

# 46. ЛОКАЛИЗАЦИЯ ДЛЯ УЗБЕКИСТАНА

Основной язык макета — русский.

Предусмотри узбекский язык на латинице.

### Учитывай

- Имена на узбекской латинице.
- Имена на кириллице.
- Смешанные написания.
- Номера +998.
- Районы Ташкента.
- Типы недвижимости.
- Валюты UZS и USD.
- Форматы дат.
- Часовой пояс Asia/Tashkent.

### Не делай

- Автоматического переименования клиентов при переключении языка.
- Скрытой конвертации валют.
- Подмены отсутствующего района значением «Ташкент».
- Автоматической смены страны номера по текущему расположению устройства.

### Даты

В продукте:
- «Сегодня».
- «Вчера».
- «24 окт.»
- «24.10.2025» при необходимости.

Все значения вычисляются из фактических временных данных.

# 47. КОНФИДЕНЦИАЛЬНОСТЬ И ЗАКОНОДАТЕЛЬСТВО

CRM содержит персональные данные.

Предусмотри Privacy by Design.

### Обязательные принципы

- Минимизация собираемой информации.
- Обоснованные цели обработки.
- Права на просмотр и изменение.
- Разделение личной и корпоративной информации.
- Ограничение экспорта.
- Проверяемые операции изменения.
- Разрешённые источники данных.
- Безопасное хранение.
- Корректные сроки хранения и удаления.
- Защита от случайного раскрытия.
- Отсутствие автоматического скрытого импорта личных контактов.

### Не требуй в обычной карточке

- ПИНФЛ.
- Паспорт.
- Домашний адрес.
- Банковские реквизиты.
- Данные членов семьи.

Если они необходимы в отдельном разрешённом процессе сделки, это не основание собирать их при обычном создании CRM-контакта.

### Узбекистан

Юридическая и инфраструктурная команды должны проверить действующий Закон «О персональных данных», в том числе изменения по Закону № ЗРУ-1125 от 26 марта 2026 года.

Учитывай, что правила могут различаться по категориям персональных данных и условиям их обработки и хранения.

Не делать упрощённого утверждения, что все клиентские данные обязательно хранятся только в Узбекистане или, наоборот, всегда могут свободно передаваться за рубеж.

Необходимы отдельная правовая проверка, классификация данных и подтверждение архитектуры.

# 50. OFFLINE STATES

Показать:

**«Нет соединения»**

«Показаны последние сохранённые данные. Изменения могут быть недоступны».

**«Обновлено в 10:42»**

- Предотвращать дубли.

- Показывать реальный результат.

### Если offline queue отсутствует

Не обещать гарантированное сохранение изменений.

Стиль: спокойный, быстрый, системный.

Мягкое появление Header и списка.

### Поиск

Локальное обновление результатов.

Без резкого мерцания всей страницы.

### Выбор сегмента

Короткая смена состояния chip.

### Открытие клиента

Плавный переход к Client 360°.

### Открытие Quick Actions

Небольшой Bottom Sheet.

### Назначение ответственного

Короткий pending-state и подтверждение.

### Добавление клиента

Плавное появление новой строки после реального сохранения.

### Изменение фильтра

Сохранение текущей позиции или предсказуемый переход к началу новой выдачи.

Не перемещать строку пользователя резко во время чтения.

Локальный текст рядом с действием.

Отключать декоративные перемещения.

- Конфетти.

- Длинные вступительные заставки.
- Бесконечные анимации «важности клиента».
- Случайное изменение расположения карточек.

На первом viewport:

Время от начала поиска до открытия нужной карточки.

**Search Success Rate**

Доля поисковых сессий, в которых пользователь открыл подходящий результат.

**Duplicate Contact Rate**

Доля действительно подтверждённых дублей в доступной CRM.

**Client Action Coverage**

Доля активных клиентов, имеющих понятный следующий шаг.

**Client Context Completeness**

Наличие достаточных рабочих сведений, без сбора лишних персональных данных.

**CRM Activation Rate**

Доля созданных клиентов, по которым затем выполнено полезное рабочее действие.

**Client Profile Return Rate**

Частота повторного открытия рабочих карточек для продолжения процесса.

**Assignment Coverage**

Доля доступных командных клиентов с назначенным ответственным, когда это предусмотрено процессом.

**Data Access Error Rate**

Частота ошибок доступа и конфликтов.

**Bulk Action Error Rate**

Доля массовых изменений, завершившихся частичными ошибками.

### Принцип

Большое число контактов в CRM не означает успешную работу риэлтора.

Главная ценность — качество работы с реальными клиентскими возможностями.

# 63. ФИНАЛЬНАЯ UX-ЦЕЛЬ

Создай **премиальный, минималистичный и практически полезный экран «База клиентов / CRM»**, который станет основной точкой доступа ко всей клиентской работе риэлтора.

Пользователь должен быстро отвечать на вопросы:

**Кого я ищу?**

**Есть ли этот человек в моей CRM?**

**Что он хочет?**

**Когда мы общались?**

**Какой следующий шаг?**

**Как быстро связаться с ним?**

**Есть ли у него другие запросы?**

**Кто отвечает за клиента?**

Главная задача не в том, чтобы показать больше CRM-полей.

Главная задача — помочь быстро найти человека, восстановить рабочий контекст и продолжить процесс.

**CRM SuperApp — не просто список контактов. Это организованная клиентская база, связанная с обращениями, запросами, объектами, диалогами и действиями.**

Главная эмоция пользователя:

**«Я легко нахожу любого доступного мне клиента, вижу его текущую ситуацию и знаю, что делать дальше».**

Финальный результат — один полностью проработанный экран №13 со всеми состояниями, клиентскими строками, поиском, фильтрами, сегментами, ролевой логикой, безопасным управлением данными, техническими ограничениями, адаптивностью, доступностью, анимациями, Figma-структурой и критериями приёмки.

**Подготовь законченный профессиональный UX/UI-дизайн и подробную спецификацию для команды SuperApp.**
