# 02. ФИЛОСОФИЯ SUPERAPP

SuperApp — интеллектуальная рабочая система риэлтора, которая помогает не упускать клиентов, находить подходящие объекты и доводить рабочие возможности до сделок.

Долгосрочная философия продукта — **«смартфон для бизнеса»**.

Есть общая инфраструктура, а профессиональные модули подключаются независимо.

Основные компоненты:

- Клиентская база / CRM.
- Единый Inbox.
- Lead Shield.
- Client 360°.
- Задачи и Follow-up.
- Property Hub.
- Smart Match.
- Showing Manager.
- Deal Management.
- Commission Tracking.
- Analytics.
- AI Copilot.

Property Hub должен быть самостоятельным полезным модулем.

Риэлтор может пользоваться им без AI, без автоматической публикации объявлений и без доступа к внешним каталогам.

### Главный принцип

**Собственная база недвижимости — это управляемые рабочие данные, а не бесконтрольный поток объявлений из интернета.**

В MVP пользователь должен иметь возможность вручную добавлять и находить объекты, обновлять их статус, контролировать актуальность и связывать с клиентами.

# 03. ГЛАВНАЯ UX-ЦЕЛЬ

Риэлтор открывает Property Hub и за 3–5 секунд должен понимать:

1. Где находится поиск.
2. Сколько объектов доступно в текущем рабочем пространстве.
3. Какие предложения доступны для работы.
4. Какие требуют проверки.
5. Как отфильтровать недвижимость по запросу клиента.
6. Как открыть конкретный объект.
7. Как связать его с клиентом.
8. Как добавить новый объект.

Главная эмоция:

**«Вся моя недвижимость под рукой. Я быстро нахожу подходящие варианты и понимаю, каким предложениям можно доверять».**

Вторая эмоция:

**«Я не предложу клиенту заведомо снятый или давно не проверенный объект по ошибке».**

Интерфейс должен экономить время, но не обещать невозможной абсолютной актуальности.

# 04. КЛЮЧЕВОЕ РАЗДЕЛЕНИЕ: PROPERTY И LISTING

До проектирования интерфейса различай несколько сущностей.

## Property / Объект недвижимости

Физический объект: конкретная квартира, дом, земельный участок или коммерческое помещение.

## Listing / Предложение

Коммерческое предложение по объекту: продажа или аренда на определённых условиях.

## Property Source / Источник

Откуда поступили сведения:
- Добавлены риэлтором.
- Добавлены агентством.
- Получены от собственника.
- Импортированы через разрешённую интеграцию.
- Внесены по внешней ссылке как справочная информация.

## Availability / Доступность

Доступен ли объект для определённой операции в текущем рабочем контексте.

## Freshness / Актуальность сведений

Когда и что в последний раз было проверено.

## Verification / Подтверждение

Какая конкретная характеристика подтверждена и каким способом.

## Publication / Публикация

Где объект размещён и кому виден.

### Главное правило

**Один физический объект может иметь несколько предложений и несколько источников информации.**

Например:
- Одна квартира предлагается на продажу.
- Позднее она может предлагаться в аренду.
- Одну квартиру могут вести несколько сотрудников.
- Сведения могли поступить от разных агентств.

Не объединяй физические объекты автоматически только по похожим фотографиям, адресу или цене.

Не смешивай «объект в базе» и «публичное объявление».

# 05. ОСНОВНОЕ UX-РЕШЕНИЕ

Property Hub — это **рабочий каталог с приоритетом поиска и актуальности**.

Каждая карточка должна отвечать:

**Что за недвижимость?**

**Где находится?**

**Сколько стоит?**

**Для какой операции доступна?**

**Когда сведения проверялись?**

**Что я могу сделать с этим объектом?**

Не создавай интерфейс, похожий на бесконечную рекламную ленту маркетплейса.

Риэлтору важнее найти объект и начать действие, чем листать красивые фотографии без информации об актуальности.

# 09. РАБОЧИЕ ПРОСТРАНСТВА

Для самостоятельного риэлтора показывать его собственную базу.

Для агентства учитывать корпоративную базу и роли.

### Возможный переключатель

**«Мои» / «Агентство»**

Показывать только при наличии соответствующих прав.

### Мои

Объекты, которыми управляет пользователь либо которые ему назначены.

### Агентство

Доступная пользователю часть корпоративной базы.

### Дополнительные пространства

Если у пользователя есть личная и корпоративная базы, предусмотри явный выбор рабочего пространства.

### Главное правило

Личный объект не становится объектом агентства автоматически.

Передача или публикация в общей базе требует допустимого действия и соответствующих прав.

### При переключении

- Обновить поиск.
- Пересчитать счётчики.
- Обновить доступные объекты.
- Проверить права.
- Не показывать кэшированные закрытые данные предыдущего пространства.

# 10. ОБЛАСТЬ B — КОМПАКТНАЯ СВОДКА

Покажи максимум три показателя.

Демонстрационный пример:

**84 — Объекта**

**62 — Доступны**

**11 — Требуют проверки**

### Объекта

Количество доступных пользователю записей в выбранном пространстве в рамках явно определённой области учёта.

### Доступны

Количество объектов или предложений со статусом доступности «Доступен», согласно определённой модели.

### Требуют проверки

Предложения с неизвестной, просроченной по установленному правилу или требующей повторного подтверждения актуальностью.

### Важно

Категории могут пересекаться.

Объект может быть помечен «Доступен», но при этом требовать повторной проверки.

Не суммируй все три показателя.

### Если данные недоступны

Показывать «Нет данных», а не фиктивный ноль.

### Поведение

Нажатие на показатель применяет соответствующий фильтр.

# 12. ОБЛАСТЬ D — БЫСТРЫЕ СЕГМЕНТЫ

Горизонтальные chips:

**«Все» | «Доступны» | «Требуют проверки» | «Забронированы» | «Архив»**

### По умолчанию

«Все».

### Визуально

Выбранный сегмент — чёрный.

Остальные — светло-серые.

### Семантика

**Все**

Все доступные пользователю неархивные записи в текущем пространстве.

**Доступны**

Предложения с рабочим статусом доступности.

**Требуют проверки**

Объекты с неактуальными или недостаточно подтверждёнными данными по утверждённым правилам.

**Забронированы**

Объекты с реально зафиксированной бронью или удержанием, если процесс предусмотрен.

**Архив**

Записи, выведенные из активной базы.

### Важное правило

«Забронирован» не должен означать существование юридически действующего бронирования по одному клику без соответствующего процесса.

Если в MVP нет системы бронирования, можно использовать более нейтральный статус:

**«Предварительно занят»**

Только если такой статус ясно определён как рабочая отметка, а не юридическое обязательство.

# 13. РЕЖИМ ОТОБРАЖЕНИЯ

Основной мобильный режим:

**«Список»**

Дополнительный режим, если действительно реализована географическая функция:

**«Карта»**

Используй компактный переключатель:

**«Список» / «Карта»**

### Рекомендация для MVP

Список — основной и обязательный режим.

Карта — необязательное развитие.

### Важно

Не добавляй карту исключительно ради внешнего впечатления.

Для карты нужны:
- Географические координаты.
- Правомерные источники картографических данных.
- Качественная геокодировка.
- Права на отображение адресов.
- Контроль неточных локаций.
- Обработка ошибок геокодирования.

### Если координаты неизвестны

Не ставь объект в центр Ташкента как будто это его реальная точка.

Показывать:

**«Точное местоположение не указано»**

# 14. ОБЛАСТЬ E — СОРТИРОВКА

Рядом с результатами:

**«Сортировка: новые»**

Варианты:
- «Сначала новые».
- «Недавно обновлённые».
- «Цена: по возрастанию».
- «Цена: по убыванию».
- «Недавно проверенные».
- «Давно не проверялись».

### Сначала новые

По дате создания записи в текущей базе, а не по предполагаемой дате строительства здания.

### Недавно обновлённые

По фактическому изменению рабочих данных.

### Цена

Только в рамках корректно сопоставимых предложений.

Не смешивать:
- Покупку и месячную аренду.
- USD и UZS без ясной модели курса.
- Цена за м² и полную цену.
- Коммерческую аренду в разных единицах времени.

### Недавно проверенные

По времени последнего подтверждения конкретного набора параметров.

### Давно не проверялись

Приоритет неизвестных и устаревших сведений должен быть явно определён.

Не считать дату создания объекта датой последней проверки.

**«Фильтры объектов»**

- Продажа.
- Аренда.
- Все.

Если проект поддерживает дополнительные модели аренды, отображать их отдельно и понятно.

### 2. Тип недвижимости

- Квартира.
- Дом.
- Коммерческое помещение.
- Земельный участок.
- Другое.

### 3. Город и район

- Ташкент.
- Районы Ташкента.
- Другие города, если данные доступны.

Поддерживать несколько районов.

### 4. Цена

- От.
- До.
- Валюта.

Смысл цены зависит от операции.

Продажа:
**«Полная цена»**

Аренда:
**«В месяц»**, если это действительный тип расчёта.

### 5. Количество комнат

- 1.
- 2.
- 3.
- 4+.
- Любое.

Различай «Любое» и «Не указано» в данных.

### 6. Площадь

**«Площадь, м²»**

Минимум и максимум.

Для земельных участков поддерживать подходящие единицы: м², сотки или гектары, с однозначным переводом для фильтрации.

### 7. Этаж

- От.
- До.

### 8. Этажность здания

Отдельный параметр.

Не смешивать этаж квартиры и количество этажей здания.

### 9. Тип рынка

- Новостройка.
- Вторичное жильё.
- Не указано.

Только для применимых категорий недвижимости.

### 10. Статус доступности

- Доступен.
- Предварительно занят / забронирован.
- Продан.
- Сдан.
- Временно недоступен.
- Неизвестно.

### 11. Актуальность

- Подтверждена недавно.
- Требует проверки.
- Никогда не подтверждалась.
- Проверена за выбранный период.

«Недавно» должно определяться настоящим правилом, а не декоративной меткой.

### 12. Источник

- Добавлено вручную.
- Моя база.
- Агентство.
- Разрешённый импорт.
- Собственник.
- Другой источник.

### 13. Ответственный

- Я.
- Доступные сотрудники.
- Без ответственного.
- Все разрешённые.

### 14. Дополнительные характеристики

Показывать только действительно индексируемые поля:
- Мебель.
- Парковка.
- Лифт.
- Состояние ремонта.
- Отдельный вход.
- Назначение коммерческого помещения.
- Другие структурированные характеристики.

Не добавляй в фильтры поля, по которым backend фактически не умеет искать.

### Действия

**«Показать объекты»**

Вторичная:

**«Сбросить»**

Не применять изменения из Bottom Sheet до явного нажатия, если выбрана модель подтверждённого применения.

# 16. ЛОГИКА ФИЛЬТРОВ

Определи правила сочетания:

- Разные группы параметров соединяются логическим AND.
- Несколько выбранных районов внутри одного поля обычно соединяются OR.
- Несколько типов недвижимости внутри одного поля соединяются OR.
- Пустые значения не подменяются нулём.
- Диапазоны включают границы или используют явно определённую семантику.
- Неизвестная цена не считается ценой 0.
- Неизвестная площадь не считается площадью 0 м².

### Если фильтры несовместимы

Например, пользователь выбрал земельные участки и фильтр количества комнат.

Скрыть неуместное поле или корректно объяснить его неприменимость.

### Если выбран смешанный тип операции

Не применять один диапазон цены одновременно к покупке и аренде без ясного указания смысла.

### Сохранение контекста

После открытия объекта и возврата:
- Сохраняй фильтры.
- Сохраняй сортировку.
- Сохраняй поисковый запрос.
- По возможности сохраняй позицию списка.

# 21. СТАТУСЫ ДОСТУПНОСТИ

Разработай простую и расширяемую систему.

### Доступен

Предложение считается доступным по последним известным данным.

### Предварительно занят / Забронирован

Есть допустимая рабочая отметка о временном удержании или брони.

Не означает юридически подтверждённый договор, если отдельный процесс не выполнен.

### Временно недоступен

Объект временно нельзя предлагать.

### Продан

Предложение о продаже закрыто по соответствующему подтверждению.

### Сдан

Предложение об аренде закрыто по соответствующему подтверждению.

### Снят с предложения

Объект больше не предлагается в этом рабочем контексте.

### Неизвестно

Доступность не подтверждена.

### Архив

Запись исключена из активного каталога, но сохраняется в допустимой истории.

### Принцип

Статус «Продан» и «Сдан» относятся к соответствующим коммерческим предложениям, а не к уничтожению физического объекта из системы.

# 22. АКТУАЛЬНОСТЬ ОБЪЕКТА

Разработай отдельный компонент:

**Freshness Indicator**

### Пример состояний

**«Проверено сегодня»**

**«Проверено 24 октября»**

**«Требует проверки»**

**«Никогда не проверялось»**

**«Источник недоступен»**

### Но обязательно укажи, что было проверено

В деталях:

- Цена.
- Наличие.
- Условия.
- Контакты собственника.
- Возможность показа.

### Пример

**«Наличие подтверждено собственником сегодня»**

Отдельно:

**«Цена последний раз уточнялась 20 октября»**

Это более достоверно, чем общая фраза «Объект полностью проверен».

### Главное

Не смешивай:
- Обновлено в CRM.
- Проверено у собственника.
- Проверено по документам.
- Получено обновление от импортного источника.
- Проверена государственная выписка.

Это разные события и уровни подтверждения.

# 23. КАК ОПРЕДЕЛЯЕТСЯ «ТРЕБУЕТ ПРОВЕРКИ»

Для MVP предложи настраиваемое правило свежести.

Например:
- Для аренды — одна рабочая периодичность.
- Для продажи — другая.
- Для активно рекламируемых предложений — более частая проверка.

### Важно

Не устанавливай универсальные 7 дней как доказанный отраслевой стандарт.

Порог должен определяться:
- Типом операции.
- Бизнес-правилами.
- Настройками агентства.
- Источником данных.
- Реальным процессом обновления.

### После истечения порога

Показывай:

**«Требует повторной проверки»**

Но не переводить автоматически объект в статус «Сдан» или «Продан».

Отсутствие обновления не доказывает недоступность.

### Если подтверждение устарело

Пользователь может:
- Проверить.
- Создать задачу.
- Отметить результат.
- Ограничить отправку клиентам, если политика агентства это предусматривает.

- Сотрудник агентства.

**«Контакт собственника не указан»**

- Есть разрешённый номер или канал.

- Источник доступен.

Наличие телефона в CRM не означает подтверждённого права человека распоряжаться недвижимостью.

Роль «Собственник» может быть рабочей записью, которую ещё нужно проверить.

# 28. ИМПОРТ ВНЕШНИХ ОБЪЯВЛЕНИЙ

Для MVP не предполагай, что существует официальный API любого сайта объявлений.

### Возможные сценарии

- Ручной ввод.
- CSV, если поддерживается.
- Партнёрский API при наличии соглашения.
- Ссылочная запись на внешний объект.
- Данные из корпоративной системы с разрешённой интеграцией.

### Ключевое ограничение

Нельзя считать, что SuperApp имеет право автоматически массово скачивать объявления, фотографии, телефоны собственников и тексты с любых внешних порталов.

Нужны:
- Право доступа к данным.
- Условия API.
- Право на хранение.
- Право на повторное использование.
- Условия публикации.
- Права на фотографии.
- Правомерная обработка персональных данных.

### Если пользователь вставляет ссылку

Не обещай автоматический импорт всех полей.

Допустимый MVP:

**«Сохранить ссылку на источник»**

И дополнительные поля, заполненные вручную.

### Если импорт поддерживается

Показывать подтверждённые результаты импорта.

Не создавать фальшивую синхронизацию с внешним сайтом.

# 29. ГОСУДАРСТВЕННЫЕ КАДАСТРОВЫЕ ДАННЫЕ

Для рынка Узбекистана юридическая проверка недвижимости особенно важна.

Но Property Hub не должен автоматически выдавать собственную карточку за государственно проверенную запись.

### Различай

**«Данные внесены риэлтором»**

**«Собственник подтвердил сведения»**

**«Документ предоставлен»**

**«Документ проверен пользователем»**

**«Проверка через государственный источник выполнена»**, только если есть действительный подтверждённый результат.

### Важно

Наличие официального сервиса проверки кадастровой выписки не означает, что SuperApp уже имеет право или техническую возможность автоматизированного получения государственных сведений через API.

Если интеграции нет:
- Предусмотри допустимый переход к официальному сервису.
- Позволь зафиксировать результат проверки вручную.
- Явно обозначай происхождение записи.
- Не присваивай зелёный бейдж «Юридически чист» по одному клику.

### Никогда не обещай

- Гарантированное право собственности.
- Отсутствие всех обременений.
- Отсутствие судебных споров.
- Юридическую готовность сделки.

Без действительной комплексной проверки.

# 30. ГЕОЛОКАЦИЯ И КАРТА

Если предусмотрен режим карты, обязательно разделяй:

### Точная точка

**«Не указано»**

- Всем сотрудникам.
- Клиентам.
- Публичным пользователям.
- В общих экспортных файлах.

Без предусмотренных прав.

### Геокодирование

Внешние геосервисы имеют:
- Ограничения API.
- Стоимость запросов.
- Квоты.
- Правила хранения результатов.
- Требования атрибуции.
- Условия отображения карт.

Не закладывать бесплатную неограниченную геокодировку как гарантированную возможность.

Список объектов продолжает работать.

# 67. ФИНАЛЬНАЯ UX-ЦЕЛЬ

Создай **премиальный, минималистичный и интеллектуальный рабочий каталог недвижимости**, который помогает риэлтору быстро находить доступные объекты, понимать достоверность сведений и связывать предложения с клиентскими запросами.

Экран должен отвечать на вопросы:

**Какие объекты у меня есть?**

**Что сейчас доступно?**

**Где находится объект?**

**Сколько он стоит?**

**Когда проверялись цена и наличие?**

**Откуда получены сведения?**

**Кто отвечает за объект?**

**Можно ли предложить его клиенту?**

**Что нужно проверить перед отправкой?**

**Какой объект подходит под конкретный запрос?**

Не создавай красивый, но бесполезный маркетплейс объявлений.

Создай **надёжную рабочую базу недвижимости**, которая становится фундаментом Smart Match, подборок, показов и будущих сделок.

**Ключевая продуктовая ценность: SuperApp помогает не просто хранить недвижимость, а поддерживать её данные в рабочем состоянии и использовать их для реальных клиентов.**

Главная эмоция:

**«Я быстро нахожу подходящий объект, понимаю его актуальность и могу уверенно продолжить работу с клиентом».**

Финальный результат — один полностью спроектированный экран №14 со всеми состояниями, карточками недвижимости, поиском, фильтрами, сортировкой, управлением актуальностью, источниками данных, правами, CRM-связями, техническими ограничениями, микроанимациями, доступностью, Figma-структурой и критериями приёмки.
