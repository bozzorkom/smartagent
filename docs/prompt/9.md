# 01. РОЛЬ ДИЗАЙНЕРА

Действуй как Principal Product Designer, Senior Mobile UX/UI Designer, UX Architect и эксперт по PropTech, мобильным CRM, Lead Management, Customer Discovery и рабочим приложениям уровня Apple.

Спроектируй **один полноценный мобильный экран №09 «Новая заявка»** и все его необходимые состояния.

Этот экран предназначен для быстрого сохранения нового рабочего обращения о недвижимости.

Пользователь должен иметь возможность:

- Создать заявку из ручного ввода.
- Создать заявку из события Inbox.
- Создать заявку после входящего или пропущенного звонка.
- Связать обращение с существующим клиентом.
- Создать нового клиента при необходимости.
- Указать покупку, аренду, продажу или сдачу объекта.
- Зафиксировать известные потребности.
- Отметить неизвестные параметры, не выдумывая значения.
- Назначить ответственного.
- Создать следующее действие.
- Сохранить заявку без длинной обязательной анкеты.
- Продолжить уточнение позднее.

Разработай high-fidelity макет, интерактивный Figma-прототип, состояния ошибок и подробную UX-спецификацию.

**Проектируй один экран, а не многошаговый мастер из нескольких страниц.**

Допускается использовать условно раскрываемые блоки, короткие Bottom Sheets, модальные подтверждения и локальные состояния.

Не создавай отдельные полноразмерные экраны Client 360°, Property Hub, Smart Match или Tasks.

**Не пиши программный код.**

# 02. ПРОДУКТОВАЯ ФИЛОСОФИЯ SUPERAPP

SuperApp — интеллектуальная рабочая система риэлтора, которая помогает не упускать клиентов, находить подходящие объекты и доводить рабочие возможности до сделок.

Долгосрочная философия продукта — **«смартфон для бизнеса»**.

Единая базовая инфраструктура дополняется независимыми профессиональными модулями.

Основные модули:

- Lead Shield.
- Unified CRM Inbox.
- Client 360°.
- AI Client Rescue.
- Today.
- Property Hub.
- Smart Match.
- Showing Manager.
- Deal Management.
- Commission Tracking.
- Agency Tools.
- Analytics.

Но пользователь не должен видеть сложность всей экосистемы, когда ему нужно просто сохранить звонок нового клиента.

### Главная продуктовая мысль

**Сначала сохранить возможность. Затем постепенно уточнить информацию. После этого довести её до полезного действия.**

Именно так должен работать экран новой заявки.

# 03. ОСНОВНАЯ UX-ЦЕЛЬ

Типичная ситуация:

Риэлтор разговаривает по телефону.

Клиент говорит:

«Нужна двухкомнатная квартира на Чиланзаре, аренда, до 600 долларов. Есть что-нибудь?»

Риэлтору необходимо быстро сохранить:

- Кто обратился.
- Как с ним связаться.
- Что он ищет.
- Какой бюджет.
- Что нужно сделать дальше.

Он не должен во время разговора заполнять 20 обязательных полей.

### Целевой пользовательский результат

За ориентировочно **15–30 секунд** пользователь должен иметь возможность сохранить простую заявку при наличии базовых сведений.

Это целевой показатель для UX-тестирования, а не обещание гарантированного времени для каждого пользователя.

Подробная квалификация может занять больше времени, но не должна быть обязательной для первичного сохранения.

### Главное ощущение

**«Я быстро сохранил клиента, его запрос и следующий шаг. Теперь ничего не нужно держать в голове».**

# 04. ВАЖНО: РАЗДЕЛЯЙ СУЩНОСТИ

Перед проектированием UI необходимо различать три понятия.

## Контакт / Client

Человек или организация, с которыми риэлтор взаимодействует.

Пример:

«Мадина К.»

Контакт может иметь:
- Имя.
- Несколько телефонов.
- Telegram.
- WhatsApp.
- Instagram.
- Историю общения.

## Обращение / Lead

Конкретная рабочая возможность или входящее обращение.

Пример:

«Клиент обратился с вопросом об аренде квартиры».

Обращение имеет:
- Источник.
- Время.
- Рабочий статус.
- Ответственного.
- Связь с контактами и событиями.

## Запрос / Requirement

Потребность клиента в недвижимости.

Пример:

«Аренда двухкомнатной квартиры на Чиланзаре до $600 в месяц».

У одного человека может быть несколько запросов.

У одного запроса могут быть несколько связанных звонков, сообщений, объектов и задач.

### Главное правило

**Не создавай нового клиента автоматически на каждую новую заявку.**

Если клиент существует, можно создать новую заявку, связанную с ним.

Не перезаписывай прежний запрос новыми параметрами без явного выбора пользователя.

Не объединяй обращения только на основании похожих имён.

# 05. КЛЮЧЕВОЕ UX-РЕШЕНИЕ

Один экран с тремя основными блоками:

**1. Кто обратился?**

**2. Что нужно?**

**3. Что делаем дальше?**

Все остальные поля — второстепенные.

### Принцип Progressive Disclosure

Показывать сначала только самое необходимое.

Дополнительные поля раскрываются:
- После выбора типа операции.
- После выбора типа недвижимости.
- При нажатии «Больше параметров».
- Когда пользователь сам решает уточнить запрос.

Не открывать сразу десятки пустых полей.

### Рекомендуемое поведение

Риэлтор может:

**Быстро сохранить** заявку с минимально известными данными.

Или:

**Уточнить подробности**, если клиент готов рассказать больше.

Оба сценария должны приводить к сохранению одной и той же корректной CRM-сущности.

# 08. ОБЛАСТЬ A — HEADER

Слева:

Кнопка назад либо закрытия, в зависимости от способа открытия.

По центру или слева:

**«Новая заявка»**

Справа:

Текстовое действие:

**«Отмена»**

Не дублируй две одинаковые кнопки закрытия без необходимости.

### Если форма открыта из Inbox

Закрытие возвращает пользователя:
- К исходному обращению.
- С прежним фильтром.
- С сохранённой позицией списка.

### Если форма открыта из Client 360°

Закрытие возвращает к тому же клиенту.

### Если форма открыта из Caller ID

Закрытие возвращает к допустимому состоянию звонка или рабочей истории, если контекст ещё существует.

### Несохранённые изменения

Если пользователь заполнил данные и нажал «Отмена», показать подтверждение:

**«Закрыть без сохранения?»**

Описание:

**«Введённые данные могут быть потеряны».**

Кнопки:
- «Продолжить заполнение».
- «Закрыть без сохранения».

Если поддержан защищённый черновик, допускается отдельный вариант «Сохранить черновик».

Не показывай предупреждение, если пользователь ничего не вводил.

# 09. ОБЛАСТЬ B — ИСТОЧНИК ОБРАЩЕНИЯ

Если заявка создаётся из существующего события, покажи компактный блок под Header.

Примеры:

**«Источник: Telegram Business»**

**«Получено сегодня, 10:42»**

или:

**«Источник: Пропущенный рабочий звонок»**

**«Сегодня, 14:12»**

### UI

Одна небольшая светло-серая карточка:

- Иконка источника.
- Название.
- Время.
- Подпись «Связано с обращением».
- Кнопка «Посмотреть источник», если доступна.

### Главное правило

Источник, полученный от интеграции, — системное происхождение события.

Не предоставляй пользователю возможность произвольно изменить технический факт:

«Telegram» → «Instagram».

Можно добавить отдельное поле **«Как узнал о нас?»**, но оно не должно подменять подтверждённый технический источник.

### Если заявка создаётся вручную

Небольшая подпись:

**«Добавлено вручную»**

При желании пользователь может выбрать заявленный источник обращения:

- Звонок.
- Telegram.
- WhatsApp.
- Instagram.
- Рекомендация.
- Сайт / реклама.
- Другое.
- Неизвестно.

Но этот выбор фиксируется как **указано пользователем**, а не как подтверждённое событие интеграции.

### Если источник недоступен

Показывать:

**«Источник не определён»**

Не заполнять его догадкой.

# 11. ФОРМА НОВОГО КОНТАКТА

Если пользователь создаёт нового клиента, раскрываются два поля.

## Поле 1 — Имя

Label:

**«Имя клиента»**

Placeholder:

**«Как обращаться к клиенту?»**

Необязательное при наличии другого достаточного идентификатора.

## Поле 2 — Телефон

Label:

**«Телефон»**

Слева по умолчанию:

**+998**

Placeholder:

**«90 123 45 67»**

### Поведение

- Поддержка вставки международного номера.
- Нормализация и корректная проверка формата.
- Не дублировать префикс +998.
- Не считать корректную маску доказательством, что номер принадлежит клиенту.
- Не считать номер подтверждённым SMS-верификацией только потому, что его ввёл риэлтор.

Если SuperApp работает с международными клиентами, возможность других стран допускается только при поддержке продуктом и соответствующей проверкой.

### Дополнительный необязательный способ связи

Ссылка:

**«Добавить другой контакт»**

При открытии:

- Telegram username или разрешённая связь с Telegram-контактом.
- WhatsApp-номер.
- Instagram username.

### Важная разница

Вручную введённый `@username` — это контактная заметка, а не автоматически авторизованный канал и не подтверждённый API-идентификатор.

Не показывать «Telegram подключён» только потому, что пользователь записал username клиента.

Не создавать личную переписку в SuperApp без действительного доступа.

# 12. МИНИМАЛЬНЫЕ ТРЕБОВАНИЯ К СОХРАНЕНИЮ

Нельзя требовать от пользователя все параметры недвижимости.

Но нельзя создавать полностью пустую бессмысленную заявку.

### Рекомендуемое правило

Для обычного ручного создания достаточно одного из следующих вариантов:

**A. Известный клиент.**

Выбрана существующая CRM-карточка.

**Б. Новый идентифицируемый контакт.**

Указано имя и/или поддерживаемый номер или другой допустимый контактный идентификатор.

**В. Обращение из подключённого источника.**

Есть действительный ID входящего события или разрешённого диалога, даже если имя и номер скрыты.

**Г. Заявка без контакта.**

Если данных пока недостаточно, пользователь явно выбирает:

**«Сохранить без контакта»**

В этом режиме обязательно указать короткое описание, объясняющее, что нужно сохранить.

Такая запись получает статус:

**«Нужно уточнить контакт»**

Не создавать клиента с вымышленным именем и номером.

### Сохранение без параметров недвижимости

Допускается.

В этом случае заявка получает рабочее состояние:

**«Запрос требует уточнения»**

### Важный принцип

**Неполная заявка лучше потерянного обращения, но неизвестные сведения должны оставаться неизвестными.**

# 13. ОБЛАСТЬ D — ЧТО НУЖНО?

Заголовок:

**«Что нужно клиенту?»**

Описание:

**«Выберите основное направление. Детали можно уточнить позже».**

### Первый уровень — операция

Используй крупные selectable chips либо компактные карточки.

Варианты:

**«Купить»**

**«Арендовать»**

**«Продать»**

**«Сдать в аренду»**

**«Пока не знаю»**

### Значение

«Купить» — клиент ищет недвижимость для покупки.

«Арендовать» — клиент ищет недвижимость для аренды.

«Продать» — собственник или представитель предлагает объект на продажу.

«Сдать в аренду» — собственник или представитель предлагает объект для аренды.

«Пока не знаю» — характер обращения ещё не уточнён.

Это не тождественно типу недвижимости.

### Логика

По умолчанию ничего не выбрано.

Если пользователь указал тип операции, остальные поля адаптируются.

Если изменил тип операции:
- Не удалять уже введённые сведения молча.
- Предупреждать о данных, несовместимых с новым сценарием, только когда это действительно необходимо.
- Не создавать автоматически второй запрос.

### Не смешивай роли

Собственник может одновременно быть покупателем.

Клиент может иметь несколько независимых запросов.

В этом сценарии фиксируется одна конкретная заявка с её текущей операцией.

# 14. ВТОРОЙ УРОВЕНЬ — ТИП НЕДВИЖИМОСТИ

После выбора операции появляется:

**«Тип недвижимости»**

Варианты:

- Квартира.
- Дом.
- Коммерческая.
- Земля.
- Другое.
- Пока не уточнено.

Рекомендуемый UI — компактные selectable chips.

### Условные уточнения

# 21. ОТВЕТСТВЕННЫЙ РИЭЛТОР

Если пользователь работает самостоятельно:

По умолчанию:

**«Ответственный: Вы»**

Не выводить отдельный большой список сотрудников.

Если пользователь — сотрудник агентства:

По умолчанию:
- Текущий пользователь, если разрешено брать заявки.
- Или назначенный системой сотрудник, если заявка поступила по правилам распределения агентства.

Если пользователь — руководитель:

Компактный выбор:

**«Кому назначить?»**

Варианты:
- «Себе».
- «Выбрать сотрудника».
- «Пока без ответственного».

Последний вариант доступен только в соответствии с правилами команды.

### Важные ограничения

- Смена ответственного требует соответствующих прав.
- Назначение должно подтверждаться сервером.
- Два пользователя не должны незаметно владеть одной заявкой из-за гонки запросов.
- История назначения сохраняется.
- Не передавай заявку в другое рабочее пространство без явного разрешённого сценария.

### Если сотрудник не имеет права назначать

Показать текущего ответственного.

Не рисовать активный список переназначения.

# 22. СОХРАНИТЬ И НАЧАТЬ РАБОТУ

В нижней части экрана — закреплённая CTA-панель.

Основная кнопка:

**«Сохранить заявку»**

Стиль:
- Чёрный фон.
- Белый текст.
- Полная доступная ширина.
- Высота 56 pt.
- Большой радиус.
- Системная лёгкая реакция на нажатие.

Под кнопкой:

**«Остальные детали можно добавить позже»**

### Поведение кнопки

Кнопка активна, когда выполнены минимальные требования к содержанию.

Не требовать всех параметров недвижимости.

### При нажатии

1. Проверить форму.
2. Проверить связь с клиентом.
3. Проверить возможные дубли.
4. Подготовить создание заявки.
5. При выбранном и валидном следующем действии сохранить его вместе с заявкой согласованно.
6. Выполнить серверную операцию.
7. Показать подтверждение только после успешного результата.

### Loading

Текст:

**«Сохраняем заявку…»**

Блокировать повторную отправку, но не препятствовать восстановлению после сетевой ошибки.

### Успех

Сообщение:

**«Заявка сохранена»**

Если задача создана:

**«Следующее действие добавлено»**

### После успеха

Предпочтительно переходить к:
- Client 360° для выбранного или созданного клиента.
- Либо к доступной карточке заявки, если запись сохранена без установленного контакта.

Если заявка открывалась из существующего диалога, допускается возврат в его контекст с ненавязчивым подтверждением.

Не создавать второй дубликат заявки при повторном открытии после успешного сохранения.

# 28. ДУБЛИКАТЫ И ПОИСК СОВПАДЕНИЙ

**«Возможно, клиент уже существует»**

**«Проверить»**

Не выбирать первый контакт автоматически.

### Если ввод совпал по имени

Показать только осторожную подсказку:

**«Есть похожие имена»**

### Если совпал ID исходного события

Не создавать вторую заявку без осознанного действия.

### Если пользователь хочет создать новую заявку для существующего клиента

Это допустимо.

- Какой клиент уже существует.

- Почему может возникнуть конфликт.

- Объединять личное и корпоративное пространство.
- Удалять исходные диалоги.
- Перезаписывать старые запросы без подтверждения.
- Игнорировать ограничения прав доступа.

# 29. СТАТУС НОВОЙ ЗАЯВКИ

На этапе создания заявки не заставляй пользователя изучать сложную воронку продаж.

Но система должна иметь корректное стартовое рабочее состояние.

### Базовые статусы

**«Новая»**

Заявка создана и ещё не квалифицирована полностью.

**«Требует уточнения»**

Недостаточно основных параметров.

**«В работе»**

Зафиксировано, что ответственный приступил к работе.

**«Ожидает клиента»**

Есть подтверждённое действие со стороны риэлтора, дальнейший шаг зависит от клиента.

**«Закрыта»**

Обращение завершено по зафиксированной причине.

### Принцип

Создание заявки не означает:
- Что риэлтор ответил клиенту.
- Что клиент квалифицирован.
- Что объект найден.
- Что показ назначен.
- Что сделка началась.
- Что комиссия заработана.

# 30. AI-АССИСТЕНТ ПРИ СОЗДАНИИ

AI должен ускорять ввод, а не усложнять его.

На основе разрешённого сообщения:

«Ищу двухкомнатную на Юнусабаде до $700».

AI может предложить заполнение:
- Операция: требует подтверждения, если не указана явно.
- Комнаты: 2.
- Район: Юнусабад.
- Бюджет: до $700.
- Срок: неизвестен.

### UI

Небольшой блок:

**«SuperApp нашёл возможные параметры»**

Подпись:

**«Проверьте перед сохранением»**

Кнопки:
- «Применить».
- «Не использовать».

### Не разрешается

- Автоматически придумывать тип сделки.
- Подставлять район из предположения.
- Менять валюту.
- Добавлять вымышленное имя.
- Указывать неозвученный клиентом бюджет.
- Создавать несуществующий объект.
- Автоматически отправлять сообщение.
- Создавать сделку из первого обращения.
- Обещать точную вероятность закрытия заявки.

### Если AI не подключён

Все поля работают вручную.

Экран не должен требовать AI для сохранения.

# 34. АВТОСОХРАНЕНИЕ И ЧЕРНОВИКИ

- Различение черновика и полноценной сохранённой заявки.

Не хранить чувствительные CRM-данные в открытом долговременном браузерном хранилище без анализа рисков и адекватных мер защиты.

- Имена клиентов.
- Содержимое заметок.

- Секреты интеграций.
- Конфиденциальные параметры клиента без достаточной цели и оснований.

### Основные KPI

**Time to Capture**

Медианное время от открытия формы до успешного сохранения заявки.

**Lead Capture Completion Rate**

Доля начатых созданий, завершившихся успешным сохранением.

**Duplicate Prevention Rate**

Доля предотвращённых подтверждённых дублей.

**Next Step Coverage**

Доля новых активных заявок с определённым следующим действием.

**Lead Qualification Completion**

Доля заявок с достаточными параметрами для соответствующего рабочего процесса.

**Source Traceability**

Доля заявок, для которых сохранено понятное происхождение.

**Time to First Useful Action**

Время между созданием заявки и первым подтверждённым полезным действием.

### Важно

Создание заявки — ещё не продажа и не успешная сделка.

Не оценивать продукт только по количеству созданных записей.

Основной смысл — превращать реальные рабочие возможности в обработанные обращения и последующие действия.

# 47. ФИНАЛЬНАЯ UX-ЦЕЛЬ

Создай **премиальный, минималистичный, быстрый и интеллектуальный экран «Новая заявка»**, который превращает разговор или сообщение о недвижимости в структурированную рабочую возможность.

Риэлтор не должен думать:

«Сейчас придётся заполнять огромную CRM-форму».

Он должен думать:

**«Сейчас быстро сохраню клиента, его запрос и то, что нужно сделать дальше».**

Экран должен отвечать на три простых вопроса:

**Кто обратился?**

**Что ему нужно?**

**Что мы делаем дальше?**

Вся дополнительная информация раскрывается постепенно.

Основная ценность SuperApp — не количество созданных CRM-записей.

**Главная ценность — помогать риэлтору не упускать реальные рабочие возможности и переводить их в конкретные действия.**

Финальный результат: один полностью проработанный экран №09 со всеми вариантами, состояниями, точными пользовательскими текстами, UX-логикой, интеграционными ограничениями, доступностью, анимациями, структурой Figma и критериями приёмки.

**Не пиши программный код. Подготовь законченный дизайн и спецификацию для команды SuperApp.**
